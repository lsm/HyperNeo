# Agent routing migration plan

## Scope and combinator fit

This plan covers the routing/gate functions in `packages/daemon/src/lib/agent/` that decide the SDK message and turn lifecycle. The governing architecture record is `docs/adr/0004-superpipe-pipelines.md`: one direct superpipe pipeline per business path, no pre-categorization into decision vs staged vs transform, and no new combinators.

The **routing and planning cores** (admission, classification, arbitration, route mapping) are pure, in-memory, and synchronous. They fit `decisionRun` or a raw `superpipe` transform. However, the **complete business paths** that consume these cores also include durable or async effects: a DB transaction in `persistAndEnqueueDelivery`, a mutex and awaited acknowledgment in `feedDeliverySteer`, an awaited handoff and `runRetryTeardown` in query retry, async persistence/event effects and a result-limit handoff in turn-end, and job-queue requeue mutations in the message-delivery handler. For those complete paths, the apply slices (PR 4, 7, 17, 20) may use `stagedRun` or an async `superpipe` pipeline when one of those combinators is the right fit; the routing core is still a direct `decisionRun` (or set of gate functions) inside the larger pipeline.

The right tools for this layer are:

- **`decisionRun`** — first-match-wins gate cascade for a typed `ctx.decision`. Use this for the pure, synchronous routing/planning cores and for sections of mixed pipelines whose stages can be expressed as synchronous gates.
- **Raw `superpipe` transform (`.pipe(...).end('ctx')`)** — for a pure, single-pass transform with a custom halt condition (`!dep`) and no `decision` field. This is appropriate when the output is an intermediate plan or a nullable value rather than the final `decision` of a `decisionRun`.
- **`stagedRun`** — for mixed async flows with snapshot → decide → effect → resnapshot cycles and compensation (see `packages/daemon/src/lib/space/runtime/verified-stop-flow.ts` and `spawn-flow.ts`). It is the right fit for the complete apply slices that perform durable writes, await async decisions, or run compensations.

For each function below, the plan picks the combinator that matches the existing control flow while exposing the branch order and stage contract to tests.

| Symbol | Proposed combinator | Rationale |
| --- | --- | --- |

| `query-retry-routing.ts:decideProviderTerminalCategory` | None (pure core leaf) | Regex classifier used by the terminal gate; not a pipeline on its own. |

## Existing superpipe examples to emulate

### `decisionRun` patterns

The daemon already uses `decisionRun` from `packages/daemon/src/lib/space/runtime/decision-pipeline.ts` for pure admission/routing paths. The closest examples are:

1. **`packages/daemon/src/lib/agent/turn-end-pipeline.ts`** — `decisionRun('sdk-turn-end', [...])` composes usage accounting, ack selection, and routing gates. It shows how an existing pipeline can delegate to another decision function and how a final gate can fall back to recomputing an upstream value when it is missing.
2. **`packages/daemon/src/lib/agent/message-delivery-pipeline.ts`** — `decisionRun('message-inject-delivery', [...])` and `decisionRun('message-turn-end-flush', [...])`. Shows gates that set side annotations (e.g., `reopenFailedDelivery`) without deciding, gates that delegate to context-reset/message-ownership helpers, and a final arbiter gate.
3. **`packages/daemon/src/lib/space/runtime/run-tick-decision-pipeline.ts`** — Long `decisionRun` gate list with lazy thunks for expensive facts and cheap short-circuit paths.
4. **`packages/daemon/src/lib/space/runtime/agent-message-routing-pipeline.ts`** — Short `decisionRun` with typed decision union and per-condition gates.
5. **`packages/daemon/src/lib/agent/query-retry-routing.ts`** — The current `queryRetryDecisionRun` is the pattern to extend: a `decisionRun` with a classifier gate that does **not** set `decision` and a mapping gate that does. The synchronous `decideQueryRetry` keeps this contract.

### Raw `superpipe` patterns

The daemon uses raw `superpipe` for mixed flows as well as pure transforms. Key examples are:

- **`packages/daemon/src/lib/space/runtime/external-event-steer-admission-pipeline.ts`** — `superpipe({ admissionSettled })(name).input(['ctx']).pipe(gate, 'ctx', 'ctx').pipe('!admissionSettled', 'ctx')... .end('ctx')` for a custom halt guard. A sequence of guard, enrich, partition, and finalize stages; using `decided(ctx, decision)` and a boolean guard to model early exit.
- **`packages/daemon/src/lib/space/runtime/verified-stop-flow.ts`** and **`spawn-flow.ts`** — `stagedRun` flows, not raw `superpipe`, but they show how snapshot/effect/resnapshot stages compose when the full path is mixed and async.

This is the model to copy when a site needs a `plan`- or `route`-shaped output, or when a mixed business path needs custom halt and effect stages.

### `stagedRun` patterns (model for the mixed apply slices)

- `packages/daemon/src/lib/space/runtime/verified-stop-flow.ts` — async session stop with `snapshot`/`resnapshot`, `decide`, `effect`, `halt`, and `when`-guarded branch arms.
- `packages/daemon/src/lib/space/runtime/spawn-flow.ts` — long async flow with CAS outcomes (`'won' | 'superseded'`) and compensations.

The mixed apply slices in this plan (PR 4, 7, 17, 20) follow the same pattern: a synchronous decision core is embedded in an async pipeline that performs effects and may resnapshot state.

## Per-site detailed plans

### `packages/daemon/src/lib/agent/turn-end-routing.ts:routeTurnEnd`

- **Current summary:** A 170-line hand-rolled cascade that maps a `TurnEndEvent` (`result` or `sessionState`) plus `TurnEndFlags` and `queryMode` to a `TurnEndPlan`. The plan controls idle-fencing, `finishTurn`, queue replay, suppression timer handling, and flag transitions for the next turn. It is the final routing gate inside the existing `turn-end-pipeline.ts` `decisionRun`.
- **Proposed combinator:** Review correction — do NOT create a separate `sdk-turn-end-routing` `decisionRun`. `routeTurnEnd` is the final routing gate of the ONE SDK turn-end business path, which `turn-end-pipeline.ts` already owns; extend `turn-end-pipeline.ts` directly with these routing gates (CLAUDE.md: one pipeline per business path), rather than leaving the path split across nested pipelines. The gate list below is unchanged; it joins the existing pipeline in place of the current `applyTurnEndRoutingGate` delegation.
- **Input/output snapshot design:**
  - Input (routing wrapper): `{ flags: TurnEndFlags; event: TurnEndEvent; queryMode: 'immediate' | 'manual' }`. This is a routing-only context; it does not include `usageState`, `resultUsage`, `ackRows`, etc., which belong to the full `TurnEndPipelineInput` (`packages/daemon/src/lib/agent/turn-end-pipeline.ts:24-43`).
  - Output: `TurnEndPlan`.
- **Pure core design:** Decompose the cascade into named gates, each populating `ctx.plan` WITHOUT deciding and WITHOUT overwriting: every routing gate begins with `if (ctx.plan !== null) return ctx;` (review correction: the gate predicates OVERLAP — an idle event with `clearAwaitingTrailingIdle` also reaches the default idle gate, and an armed-clear error also reaches the broader confirm gate — so unguarded later gates would overwrite the higher-priority plan before `applyFinalGate`; the self-guard preserves first-match precedence without halting the outer pipeline, so final usage/ack assembly still runs). Only the pipeline's existing `applyFinalGate` sets `decision` from `ctx.plan`.
  - `applySessionStateNonIdleGate` — `event.kind === 'sessionState' && event.state !== 'idle'`.
  - `applySessionStateClearAwaitingGate` — `event.kind === 'sessionState' && event.state === 'idle' && flags.clearAwaitingTrailingIdle`.
  - `applySessionStateSuppressedIdleGate` — `event.kind === 'sessionState' && event.state === 'idle' && flags.suppressIdleOnNextResult`.
  - `applySessionStateIdleFinishGate` — `event.kind === 'sessionState' && event.state === 'idle'` (default idle finish); the three session-state idle gates set `plan.resetThinkingTokens = true` because `sdk-message-handler.ts:1267-1269` resets token tracking for every `state === 'idle'` event, not only for the finish branch.
  - `applyResultPreRecoveryGate` — `event.kind === 'result' && event.result.isLimitRecoveryEngaged === null`.
  - `applyResultRecoveryEngagedGate` — `event.kind === 'result' && event.result.isLimitRecoveryEngaged === true`.
  - `applyResultArmedClearErrorGate` — `event.kind === 'result' && event.result.confirmsArmedClear && !event.result.isSuccess && event.result.isLimitRecoveryEngaged === false`.
  - `applyResultConfirmArmedClearGate` — `event.kind === 'result' && event.result.confirmsArmedClear && event.result.isLimitRecoveryEngaged === false`.
  - `applyResultLegacySuccessGate` — `event.kind === 'result' && event.result.isTopLevel && event.result.isSuccess && !flags.suppressIdleOnNextResult && !flags.usesSessionStateChangedTurnEnd && !flags.expectsSessionStateIdleAfterResult && event.result.isLimitRecoveryEngaged === false`.
  - `applyResultDefaultGate` — all remaining `result` cases.
  `makePlan` and `canReplay` remain private helpers used by the gates.
- **Shell/effect wiring:** The exported `routeTurnEnd(flags, event, ctx)` stays as a thin wrapper over the routing-only gate run in `turn-end-routing.ts` (returning `ctx.plan` with a `makePlan(flags)` fallback); it does NOT call the full `turn-end-pipeline.ts` runner, because it does not have the `usageState`, `resultUsage`, `ackRows`, etc. required by the full `TurnEndPipelineInput` (`packages/daemon/src/lib/agent/turn-end-pipeline.ts:24-43`). The same extracted routing gate functions are also composed directly into `turn-end-pipeline.ts`'s existing gate list in the routing position. The turn-end `stagedRun` (or async `superpipe`) is invoked by `handleSDKMessage` only for top-level `result` and `session_state_changed` events; the pipeline owns the `state.sdkMessages.delta` and `sdk.message` publication for those events (`packages/daemon/src/lib/agent/sdk-message-handler.ts:900-920`), while the common publication path remains for `user`, `system`, `assistant`, `status`, `compact-boundary`, and refusal messages. `handleSDKMessage` returns after the pipeline for turn-end events so each SDK message is published exactly once. The pipeline runs, in order:
  1. Persistence and pre-handoff effects (`packages/daemon/src/lib/agent/sdk-message-handler.ts:853-898`): persist the SDK message with `withDbChangeBatch(() => db.saveSDKMessage(session.id, message))` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:853-855`); if the batch fails, log a warning and, if `matchesArmedClearResult(message)`, `clearIdleSuppression()`, then short-circuit the pipeline and return (`packages/daemon/src/lib/agent/sdk-message-handler.ts:857-863`). Then compute `observesArmedClearResult` and `settlesArmedClearError` from the saved message and result; if the message matches an armed clear, `cancelSuppressedResultTimer()` before any awaited work; then for every top-level result, snapshot `activeMessageId` from the `processing` state BEFORE any awaited handoff (`packages/daemon/src/lib/agent/sdk-message-handler.ts:871-875`); then reset thinking-token tracking (`packages/daemon/src/lib/agent/sdk-message-handler.ts:880`); then, when a limit error is present, await `onResultLimitError(limitError.errorText, limitError.hint, limitError.userMessageUuid)` to determine `isLimitRecoveryEngaged`, passing the affected prompt's UUID so recovery is scheduled for the right message (`packages/daemon/src/lib/agent/sdk-message-handler.ts:877-890`, `922-937`); after the handoff completes, resnapshot the live `TurnEndFlags` (at least `suppressIdleOnNextResult` and `acknowledgedPersistedUserThisTurn`) before the routing gates, because `suppressIdleForNextResult()` or `clearIdleSuppression()` may have changed them while the handoff was pending (`packages/daemon/src/lib/agent/sdk-message-handler.ts:896-898`).
  2. `applyUsageAccountingGate` (`packages/daemon/src/lib/agent/turn-end-pipeline.ts:44-54`) produces `usage` for non-intercepted, successful top-level results. Ack selection is NOT precomputed here; the acknowledgment effect in stage 5 resnapshots eligibility immediately before consuming.
  3. The routing gates set `ctx.plan` with fields `idleFence`, `earlySetIdle`, `finishTurn`, `allowQueueReplay`, `resetThinkingTokens`, etc.
  4. Pre-publication and idle-fencing effects for turn-end events (`packages/daemon/src/lib/agent/sdk-message-handler.ts:891-920`): the `activeMessageId` from stage 1 is used for later acknowledgment matching; set `lastResultWasSuccess` and reset `lastRateLimitInfo`/`lastSdkErrorTag` before any publication (`packages/daemon/src/lib/agent/sdk-message-handler.ts:891-893`); then `beginTerminalIdle` if `plan.idleFence`; then publish `state.sdkMessages.delta` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:900-908`); then await `internalEventBus.publish('sdk.message')` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:911-920`) inside a local `try/catch` that calls `clearIdleSuppression()` and rethrows when the publication rejects and the result confirms an armed clear (`confirmsArmedClear`); this is NOT a `stagedRun` compensation, so a later failure in the successful-result side-effect stage does not unwind a second `clearIdleSuppression()` call. Review correction (PR #2980): after `internalEventBus.publish('sdk.message')` resolves, recompute the armed-clear predicate (`observesArmedClearResult` and `confirmsArmedClear`) by calling `matchesArmedClearResult(message)` against the live waiter/message state, because a subscriber or concurrent lifecycle action may have armed or cleared suppression during the await (`packages/daemon/src/lib/agent/sdk-message-handler.ts:1126`); then recompute `settlesArmedClearError = confirmsArmedClear && !isSuccess` from the resnapped match and result success so the final `clearIdleSuppression()` is driven by the live state rather than a stale pre-publication derived value; then resnapshot the live `TurnEndFlags` (including `suppressIdleOnNextResult` and `acknowledgedPersistedUserThisTurn`) and recompute the effect-facing `plan` so stage 5's `setIdle`/`earlySetIdle` and the result-side-effect gating reflect any `suppressIdleForNextResult()`/`clearIdleSuppression()` changes made by subscribers or concurrent lifecycle actions (`packages/daemon/src/lib/agent/sdk-message-handler.ts:947-950`); the pre-publication `plan.idleFence` (which gates `beginTerminalIdle`) is preserved from the first routing. The pipeline owns these two publications for the top-level `result` and `session_state_changed` events it handles; `handleSDKMessage` returns after the pipeline for those events so the message is not published again by the legacy common block. For all other SDK messages (`user`, `system`, `assistant`, `status`, `compact-boundary`, and refusal), the common publication path remains. If `isLimitRecoveryEngaged` is accepted, mark the result intercepted with the `limitBillingTerminal` flag carried from `limitError.hint.billingTerminal` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:878-883,923-930`) inside a nonfatal `try/catch` that logs and continues, then record usage, refresh context usage, and short-circuit the rest.
  5. Review correction (PR #2980): the `setIdle` step at `packages/daemon/src/lib/agent/sdk-message-handler.ts:947-950` runs for top-level `result` events when `plan.earlySetIdle`, before any result-specific side effects. Then the successful-result side effects run, gated on `event.result.isSuccess` (not a non-existent `plan.isSuccess`): run `recordResultUsageMetadata` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:1063-1118`); circuit-breaker `markSuccess` on non-zero usage; `acknowledgeOldestQueuedUserOnTurnEnd(activeMessageId, ...)` only when the resnapped `!flags.acknowledgedPersistedUserThisTurn && !flags.suppressIdleOnNextResult` (`packages/daemon/src/lib/agent/sdk-message-handler.ts:1163-1165`) — it resnapshots `activeDeliveryMessageUuids`, `hasYielded`, `hasPendingOrClaimed`, `acknowledgedPersistedUserThisTurn`, and `suppressIdleOnNextResult` immediately before `markDeliveriesConsumedAtTurnEnd`, then publishes `messages.statusChanged` and replays the consumed user messages; then reset `acknowledgedPersistedUserThisTurn` and publish `session.errorClear` (`:1147-1170`). Nested result successes are saved and published by the common publication stage but MUST NOT reach these side-effect stages. The successful-result side-effect stage is a single awaited operation that runs `recordResultUsageMetadata`, `markSuccess`, and `acknowledgeOldestQueuedUserOnTurnEnd` in sequence and has one operation-level `compensate` (or `stagedRun` unwind) that calls `clearIdleSuppression()` before rethrowing ONLY when `confirmsArmedClear` is true, matching the current `handleResultMessage` catch (`packages/daemon/src/lib/agent/sdk-message-handler.ts:1126-1134`); the same compensation is not registered on each sub-effect, because `stagedRun` reverse unwind would then invoke `clearIdleSuppression()` once per registered entry and reset a newly armed suppression.
  6. Review correction (PR #2980): after the awaited side effects in stage 5 resolve, resnapshot the live `TurnEndFlags` and recompute `plan` one more time before the final effects (`packages/daemon/src/lib/agent/sdk-message-handler.ts:1172-1179`). Turn-end idle/timer/replay/flag effects then consume that final `plan` (`finishTurn` with `setIdle` and queue replay if `plan.finishTurn && plan.allowQueueReplay`; `setIdle` with delivery/publish/callback suppression if `plan.setIdleSuppressed`; timer cancel/rearm; `settleSuppressedResultWaiter('confirmed' | 'reset')` if `plan.settleSuppressedWaiter` is set; for session-state idle events, `resetThinkingTokenTracking()` before the idle transition when `plan.resetThinkingTokens`; after the effects complete, resnapshot the live `TurnEndFlags` and merge the branch-specific resets from `plan.afterEffectsFlags` into that resnapped state while preserving any `suppressIdleOnNextResult`, `clearMessageInFlight`, or suppressed-result waiter state armed by a subscriber during the await; `void this.refreshContextUsage('turn-end')` for every SDK result, started without awaiting its promise so a slow `context.updated` publication does not block the next SDK message; `maybeRefreshContextOnEvent(message)` for `session_state_changed` events so `eventsSinceContextRefresh` is incremented and `refreshContextUsage('event-tick')` can fire at the configured interval (`packages/daemon/src/lib/agent/sdk-message-handler.ts:997`); and `clearIdleSuppression()` when the (recomputed) `settlesArmedClearError` is true).
  The final `applyFinalGate` assembles the full `TurnEndPipelineDecision`. When `turn-end-pipeline.ts` is wired into the runtime, all of these stages compose one operation, not an imperative `AgentSession` cascade consuming a decision-only fragment. Until that wiring slice lands, the gates may exist pinned by tests, but production must not be wired to a decision-only fragment.
- **Step-by-step migration:**
  1. Extract each top-level branch of the `routeTurnEnd` cascade into a named gate function in `turn-end-routing.ts` (gates are exported; `makePlan`, `canReplay`, and `resetTurnEndFlags` stay pure helpers).
  2. Extend `turn-end-pipeline.ts`'s gate list with these routing gates in the current routing position, replacing the `applyTurnEndRoutingGate` delegation to the hand-rolled cascade; keep `applyUsageAccountingGate` unchanged. Remove `applyAckSelectionGate` from the `decisionRun` so ack selection is not precomputed, and use `selectTurnEndAckRow` only inside the PR 20 acknowledgment effect that resnapshots immediately before consuming.
  3. Replace the body of `routeTurnEnd` with a call into the routing-only gate run (a `decisionRun` over the routing-only context in `turn-end-routing.ts`) and a fallback `makePlan(flags)` if `plan` is somehow null. The wrapper must not call the full `turn-end-pipeline.ts` runner, because the `routeTurnEnd` signature does not carry the full `TurnEndPipelineInput`.
  4. Confirm `turn-end-pipeline.test.ts` and `turn-end-routing.test.ts` both stay green.
- **Tests:** Keep `turn-end-routing.test.ts` as a parity suite (it already calls `routeTurnEnd`). Add `turn-end-routing-gates.test.ts` that tests each gate independently: no-op when conditions do not match, correct plan when they do, and that later routing gates PRESERVE an existing non-null `ctx.plan` (review correction: these gates set only `ctx.plan`, never `ctx.decision`, so `!hasDecided` cannot halt until `applyFinalGate`; asserting plan precedence — not decision halting — keeps the outer pipeline free to reach its final usage/ack assembly). Add a contract test that `applyDefaultResultGate` always produces a plan for any `result` not caught earlier. Ensure `turn-end-pipeline.test.ts` still passes.

### `packages/daemon/src/lib/agent/query-retry-routing.ts:classifyQueryRetryRoute`

- **Current summary:** A 37-branch cascade that classifies a query failure into one of the `QueryRetryRoute` arms (`startup_timeout_retry`, `message_not_found_retry`, `transient_retry`, `provider_backoff`, `rate_limit_handoff`, `api_validation`, `aborted_noop`, `cleanup_noop`, `superseded_noop`, `terminal`). It is the classifier gate of the query-retry pipeline and is called by `query-runner.ts` on the error hot path.
- **Proposed combinator:** Review correction — the pure classifier and finalizer gates are shared by TWO consumers, not a single runtime pipeline. They compose as one synchronous `route-query-retry` `decisionRun` (used by `decideQueryRetry` for parity and by `query-runner.ts:retryRouteChanged` for resnapshot). The SAME gate functions are embedded as decision stages inside a separate async `route-query-retry-operation` pipeline (likely a `stagedRun` or async `superpipe`) that performs the awaited effects (`onRateLimitExhausted`, `runRetryTeardown`, terminal error handling, `setIdle`). The synchronous `decisionRun` is unchanged in contract: a classifier gate sets `ctx.route`, a finalizer gate sets `ctx.decision`, and `decisionRun` halts when `ctx.decision !== null` (`packages/daemon/src/lib/space/runtime/decision-pipeline.ts:5-19`). `decideQueryRetry` and `classifyQueryRetryRoute` must remain synchronous so `retryRouteChanged` (`packages/daemon/src/lib/agent/query-runner.ts:1666-1681`) can call them and immediately inspect `route.action`.
- **Input/output snapshot design:**
  - Input: `QueryRetryRouteInput` (`errorSignal`, `env`).
  - Output: `QueryRetryDecision` (route + finalizer).
- **Pure core design:** The single pipeline runs two stage groups, linearly, with self-guarding stages (see combinator note: no `!hasRoute` halts — they would terminate the whole run). Each classifier stage is a no-op once `route` is set, so no later classifier — including the default terminal gate — can overwrite an earlier route:
  - `applySupersededClassifyGate`
  - `applyCleanupClassifyGate`
  - `applyStartupTimeoutClassifyGate`
  - `applyMessageNotFoundClassifyGate`
  - `applyTransientClassifyGate` (with `isQueryInterrupted` check)
  - `applyProviderBackoffClassifyGate`
  - `applyAbortClassifyGate`
  - `applyApiValidationClassifyGate`
  - `applyRateLimitHandoffClassifyGate` (`isRateLimit && env.hasRateLimitHandoff && rateLimitHint !== null`)
  - `applyTerminalClassifyGate` (default, calls `decideProviderTerminalCategory` and `resolveTerminalMessageHint`)

  Then the finalizer gates run against the now-set `route` (each matches at most one `route.action`).
- **Shell/effect wiring:** The pure gate functions are shared between two consumers. `decideQueryRetry(input)` stays a synchronous wrapper that runs the `route-query-retry` `decisionRun` and returns `ctx.decision`; `classifyQueryRetryRoute(input)` stays a synchronous wrapper that runs the same `decisionRun` and returns `ctx.route`. `query-runner.ts:retryRouteChanged` (`packages/daemon/src/lib/agent/query-runner.ts:1666-1680`) calls the synchronous `decideQueryRetry` with the resnapped environment and immediately reads `resnapshotted.route.action` — this resnapshot path must not become async. For the main `executeQuery` retry operation, a separate async runner (`runQueryRetryOperation`) embeds the same ten classifier and ten finalizer gate functions as direct decision stages (it does NOT invoke the synchronous `routeQueryRetryRun` wrapper) and then runs the awaited effect stages (`onRateLimitExhausted`, `runRetryTeardown`, terminal error handling, `setIdle`) so the complete business path is one direct pipeline.
- **Step-by-step migration:**
  1. Extract the pure classifier and finalizer gates as named helper functions operating on a shared `QueryRetryRoutingCtx`. They remain synchronous.
  2. Define the synchronous `routeQueryRetryRun` `decisionRun` used by `decideQueryRetry` and `classifyQueryRetryRoute`.
