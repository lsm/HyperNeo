# MessageHub client↔server message inventory

**Audited:** 2026-09-07 · **Issue:** [#3824](https://github.com/lsm/HyperNeo/issues/3824) · **Scope:** every RPC method (REQ→RSP) and every client-facing event on the MessageHub WebSocket surface.

Sources of truth (all paths relative to repo root):

- Protocol: `packages/shared/src/message-hub/protocol.ts`, `types.ts`, `message-hub.ts`
- Handlers: `packages/daemon/src/lib/rpc-handlers/` (37 of 40 files carry registrations, 297 total), `packages/daemon/src/lib/state-projection-service.ts` (7), `packages/daemon/src/lib/external-events/github/github-event-extension.ts` (15)
- Event emission: `messageHub.event(...)` call sites in `packages/daemon/src/` plus the internal-bus→client bridge `packages/daemon/src/lib/client-event-bridge.ts`
- LiveQuery: `packages/daemon/src/lib/rpc-handlers/live-query-handlers.ts`
- Client call sites: `hub.request(...)` / `callIfConnected(...)` across `packages/web/src/` (301 call sites, 215 distinct literal method strings)

**Auth model:** there is no transport-level or per-method authentication on this surface. The WebSocket (`packages/daemon/src/routes/setup-websocket.ts`) assigns a `clientId` on connect with no token handshake, and no handler performs caller-identity checks. The "gates" column in the tables below is therefore **validation and scope checking only** (existence checks, enum/range validation, message-size caps) — not authorization. Space-goal owner mutations are the one exception that inspects the caller's envelope `sessionId` — and the rule is inverted for RPC callers: global (non-`space:`) contexts are allowed while `space:`-scoped ones are denied (§ Space tasks, goals & schedules).

## 2. Wire protocol

`HubMessage` envelope (`packages/shared/src/message-hub/protocol.ts:20`):

| Field | Type | Notes |
|---|---|---|
| `id` | string | UUID per message |
| `type` | `REQ` \| `RSP` \| `EVENT` \| `PING` \| `PONG` | `MessageType` enum |
| `sessionId` | string | routing scope; `'global'` default. **Transport admission check:** any non-`global` value must resolve to an existing session (`setup-websocket.ts:124` → `getSessionForControl`), else the request is rejected with `SESSION_NOT_FOUND` *before dispatch* — a channel string like `space:…` here fails even for otherwise valid calls. Distinct from payload-level session IDs inside `data`. |
| `method` | string | dotted method/event name |
| `data` | unknown? | payload |
| `requestId` | string? | RSP only — links response to request |
| `error` / `errorCode` | string? | RSP error form |
| `channel` | string? | wire channel (§3) |
| `timestamp` | string | ISO time |
| `version` | string? | protocol `1.0.0`; **optional** — omitted on PONG heartbeats (`MessageHub.handlePing`, `setup-websocket.ts` PONG path) |
| `_transportName` | string? | internal transport metadata; the hub copies it from the request onto ordinary RPC responses (`message-hub.ts:416`) and it is **not stripped before send** — WebSocket RSP envelopes carry it on the wire |

Rules enforced by `validateMethod` (protocol.ts:85): must contain `.`, no leading/trailing `.`, no `:`, charset `[a-zA-Z0-9._-]`. PING/PONG are exempt.

Error codes (`ErrorCode`, protocol.ts:101): `INVALID_MESSAGE`, `INVALID_METHOD`, `PROTOCOL_VERSION_MISMATCH`, `METHOD_NOT_FOUND`, `HANDLER_ERROR`, `TIMEOUT`, `INVALID_PARAMS`, `INVALID_SESSION`, `SESSION_NOT_FOUND`, `TRANSPORT_ERROR`, `NOT_CONNECTED`, `MESSAGE_TOO_LARGE`, `TOO_MANY_SUBSCRIPTIONS`, `INTERNAL_ERROR`, `UNAUTHORIZED`.

Transport mechanics:

- Inbound message size cap 32 MB (`setup-websocket.ts:21`); outbound responses capped by `DEFAULT_MAX_OUTBOUND_MESSAGE_SIZE` with a `MESSAGE_TOO_LARGE` error fallback (`setup-websocket.ts:20`).
- PING→PONG heartbeat answered at hub level (`message-hub.ts:336`). The interval is configured on the **client transport**, not the hub: `WebSocketClientTransportOptions.pingInterval` (default 30000 ms, `websocket-client-transport.ts:64`) schedules the PINGs — the `pingInterval` key on `MessageHubOptions` is never read by `MessageHub`.
- Requests to unregistered methods get `METHOD_NOT_FOUND` (`message-hub.ts:378`).

## 3. Channels

Wire strings (`packages/shared/src/message-hub/channels.ts:34`):

| Wire string | Meaning | Used by |
|---|---|---|
| `global` | broadcast to all clients | most bridge events, state broadcasts |
| `session:${sessionId}` | one chat/agent session | session-lifecycle events, `state.session`, `state.sdkMessages` |
| `room:${roomId}` | multi-session room | (declared; no current emitters) |
| `space:${spaceId}` | one space | `spaceAgent.*`, `spaceGoal.ownerChanged` |
| `workflowRun:${spaceId}:${workflowRunId}` | one workflow run | (declared; no current emitters) |
| `task:${spaceId}:${taskId}` | one task | (declared; no current emitters) |

Channel-routed events reach a client only if it joined the channel (plus `global`). **Directly addressed deliveries bypass channel membership entirely**: `connection.established` is sent straight to the new client's socket on connect, and the `liveQuery.*` events are pushed to the subscribing client via `router.sendToClient`. `ClientEventGateway.publish()` (`client-event-gateway.ts:27`) converts `EventChannel` objects to these wire strings.

## 4. Events (server → client)

Three emission paths reach the client wire:

1. **Direct emission** — `messageHub.event(name, data, { channel })` at the call site.
2. **State projection broadcasts** — `StateProjectionService.broadcast*()` emits versioned state snapshots.
3. **ClientEventBridge** — internal daemon bus events mapped to client events in `packages/daemon/src/lib/client-event-bridge.ts` (payload shapes from `DaemonInternalEventMap`, `internal-event-bus.ts:461`).

4. **Directly addressed delivery** — `connection.established` is written straight to the new client's socket on connect (`setup-websocket.ts:64`), and the `liveQuery.*` events are pushed to the subscribing client via `router.sendToClient` (`live-query-handlers.ts:4611–4640`); neither passes through `messageHub.event`.

These four paths account for the 42 **statically named** events below. In addition, the test-only `test.broadcastDelta` RPC forwards its caller-controlled `channel` argument straight to `messageHub.event(...)`, so arbitrary event names can be emitted through it — the 42 is not an allowlist of every possible method string on the wire.

### 4.2 State projection broadcasts (`state-projection-service.ts`)

## 5. LiveQuery

Pull-based subscriptions over two RPC methods, pushed via the §4.4 events. The web never polls: each store registers its event listeners, then opens a subscription with a client-generated `subscriptionId`. **Ordering caveat:** the engine invokes its initial callback synchronously inside the subscribe handler (`storage/live-query.ts:253`), so the `liveQuery.snapshot` event is emitted *before* the `{ ok: true }` response is constructed — a client must register its event listener before issuing the request, or it will permanently miss the initial snapshot.

## 6. RPC methods by area

All rows are **kind: request** (client `REQ` → server `RSP`). For requests that pass envelope validation and are dispatched to a handler, errors return as `error`/`errorCode` on the RSP — **but structurally invalid envelopes are dropped silently with no response at all** (`isValidMessage` rejection in `message-hub.ts:326`, e.g. missing `timestamp` or an invalid method name): the client sees its call time out. The "web consumers" column lists the `packages/web/src/` files calling the method (`—` = no web call site; full list in §7). Type locations are abbreviated: `shared/src/...` = `packages/shared/src/...`, `daemon/...` = `packages/daemon/src/...`.
