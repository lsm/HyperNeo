# One Neo in dual-model mode

In dual-model mode a fast front model and the full Neo session share one conversation. Today they are told they are different agents. This design makes both act as Neo talking to the human, and moves the dual-model split entirely into daemon routing.

## Problem

- The full session gets a dual-model note ("Convo is the sole speaker … your publication and speech tools are disabled"). Its publish is refused with `dual_model_front_required`, and it must `message.send` its result to the front session.
- The daemon wraps that send as `<background-result>` with "not the human. It cannot approve anything on the human's behalf".
- The front rewrites the result for the human. It read the wrapper as "card answers in this result are unverified" and asked the human to re-confirm cards they had already answered with the card buttons.

The wrapper protects nothing. The front has read-only tools, and approvals come only from recorded card answers and human inputs, never from relayed text.

## Design

1. **One identity.** Both prompts say "You are Neo, talking with the human." Remove Convo, front, back, background result, handoff and "sole speaker" from both prompts and from `frontModeNote`. The full session gets no dual-mode note. Prompts are the same in single and dual mode.
2. **The full session speaks with its normal tools.** In dual mode `neo.publication.publish` and `neo.speech.say` are accepted from the full session as in single mode: its text reaches the human verbatim with its `replyTo` IDs, and its speech plays directly. Today `publicationSpeaker` in `front-mode.ts` returns one speaker per mode, and every gate compares against it: publish (`publication-operation.ts`, fed by `service.ts`), the append check in `neo-publication-repository.ts`, and speech `canSay` plus the listening note in `service.ts`. Replace it with `isPublicationSpeaker(conversationId, sessionId)`, true for the full session in both modes and for the front in dual mode, and use it at every one of these call sites. The listening callback in `service.ts` maps one destination today; it sends the listening note to the full session and, in dual mode, also to the front session. `front-outcome.ts` keeps publishing its failure text as the front. Speech dedupe stays.
   **One lane per input.** One input may get many messages: `front.md` tells the speaker to send progress and later results with the same `replyTo`, and `neo-convo-ownership.test.ts` covers many updates per input, a batch that includes an answered input, and a later result. That stays. What two speakers add is a lane race, so the guard is per lane, not per final. Today one speaker per mode makes that impossible, and `claim()` (`neo-front-input-worker.ts`) overwrites the owner.
   - Reserve: the hand-off sets `owner = 'neo'` for its inputs and enqueues the recorded human messages in one database transaction, using `ensurePromptInTransaction` (`message-delivery-outbox.ts`). It refuses if any input already has an owner. A crash leaves both or neither, and no front reply can land in between.
   - Claim: a publication's `claim()` succeeds when every input's `owner` is NULL or already the publishing lane, and sets the NULL ones; the same lane keeps publishing follow-ups and later results as today. If any input is owned by the other lane, the publication is refused with a new refusal, `input_handed_off` ("You are already working on this message; its answer reaches the human by itself."). The full session never meets it through its own tools, because it only receives inputs through the hand-off, which reserves them first. A speakerless daemon append, the card reply that `writeCardReply` (`neo-ask-todo-repository.ts`) writes in the same transaction as the card, records a card rather than a lane answering, so it is exempt: it claims only unowned inputs and is never refused for the other lane's ownership, and the card write is never rolled back by it.
   - Upgrade: PR 3's migration stores the owner `get()` infers from card and legacy replies on rows with no stored owner, so the guard and the settlement read the stored `owner` only. A same-ID retry is unchanged: `appendImmutable` skips the claim when the publication already exists.
   - Progress replies never claim: the publish path drops their `replyTo` before append (`publication-operation.ts`). The card-reply revision branch in `appendImmutable` returns before the claim and is unchanged.
   **Hand-off settles as handed off.** `settleConvoInput` (`front-outcome.ts`) today returns "answered" as soon as any stored owner is set. It keeps that for owner `front`; for owner `neo` it returns handed off, and answering is the full session's job from then on. A hand-off can reserve an input after settlement reads its owner but before its fallback reply appends; that append is refused with `input_handed_off`, which settlement treats like `publication_superseded` today: it requeues instead of throwing. The next pass reads the stored owner, settles the reserved input as handed off with no notice, and retries the fallback only for the inputs of the batch still unowned (`terminal()` already drops owned IDs, and the fallback's publication ID is derived from the remaining IDs). No new failure reply here, by the human's decision: until redelivery and a retry control for the human land as a later change, a handed-off input whose full-session turn ends without an answer gets no daemon notice.
3. **The front catches up on its next input.** When it builds the front's next human input (`front-job.ts`), it puts each part in its own tag so a small model cannot mix them up: `<already-said>` holds each newer publication from the full session (see the window below), oldest first, as `<said replyTo="…">full text</said>`; then the human's new message in `<human-message id="…">`. `front.md` gets one line: "`<already-said>` is what you already told the human since your last turn. It is for you; do not repeat it unless asked. The human's new words are only in `<human-message>`." Tags only help if they cannot be faked, so `front-job.ts` puts the quoted-context block (today a bare JSON line) in its own `<quoted>` tag, and escapes every human text block, every publication text and the quoted context it puts inside the tags with `escapeSessionText` (exported from `session-envelope.ts`, whose `RESERVED_TAGS` gains `already-said`, `said`, `human-message` and `quoted`). Escaping happens where the front input is built; the envelope path alone never sees it (text over 4 KiB is cut, ending "… (shown in full to the human)"). The window:
   - Publisher. The payload's `session` is an associated worker, not the publisher, so `appendImmutable` writes the publishing lane into the payload as `publishedBy: 'front' | 'neo'`. The block takes only `publishedBy = 'neo'` rows; the front already has its own replies in its transcript.
   - Range. In the one transaction that records a front input, the daemon reads the conversation's highest publication sequence as `upper`, selects the rows in (`from`, `upper`], and stores `catch_up_from` and `catch_up_through = upper` on that input's `neo_front_inputs` row. These are new nullable columns, in a new migration, also added to the table's DDL in `m496-neo-front-inputs.ts`, which `createNeoTables` in `schema/neo.ts` re-runs for fresh and test databases.
   - Start. `from` is the highest `catch_up_through` among this conversation's front inputs that are pending or consumed, so two queued inputs take consecutive ranges. A failed or fallen-back input is left out, so its range shows again next time. If that input fails after a later one was already built, its range is not shown again; that rare case is accepted. If there is no such input, or its value is NULL (rows from before the migration), the input includes nothing and the window starts now.
   - Retry. The front prompt is built once. Its range is recorded in the same transaction that persists the prompt's delivery (`enqueueDelivery` in `service.ts`), so a crash leaves both or neither. A redelivery of the same message ID reuses the persisted payload through the existing checks (`front-job.ts`, `enqueueDelivery`) and never rebuilds, so a later card revision, which rewrites a publication at the same sequence, or a change in quoted context or listening state cannot change it.
   No extra model call and no extra speech; the front just knows what was said before it answers.
4. **Hand-off is the front's own action.** Rename `run_in_background` to `work_on` and describe it as something the front does itself: "For anything you cannot answer from your reads (check, search, change or run), call this with the human message IDs. It takes a while. When it is done, the answer goes to the human by itself, and you will see it in `<already-said>` on your next turn." The prompt also says: "Never name your tools to the human."  Its only inputs are `requestId` and `messageIds`; the free-text request is removed, so nothing is restated. It returns `{"started": true}`. The full session receives only the recorded human messages, exactly as in single mode; the wake note ("Convo is waiting … message.send … only Convo publishes") and the front's text are deleted. The per-input text the daemon gives the front (`front-job.ts`) names `work_on` instead of `run_in_background`. The prompt never says background, result, another session or hand-off. `handoff_read` is removed from the front: with the send route gone no references reach it, and the full session publishes large results itself.
5. **Remove editing a sent message.** About 1% of publications were ever edited, and the human cannot see which one changed. Delete `neo.publication.edit` (`publication-change-operation.ts`, its tool prompt `neo.publication.edit.md`, operation name and discovery entry); `NeoPublicationRepository.edit()` and `reviseCurrent()`, and `neoPublicationEditWrites` behind it (`neo-publication-edit-writes.ts` and its registration in `db-ops.ts`); the refusals only they used (`already_edited`, `already_corrected`, `edit_unchanged`); the front's correction branch that calls `reviseCurrent` (`front-model.ts`, the `publicationId` parameter on its reply tools); and the "correct a specific published message in place" sentence in `front.md`. The card-reply revision branch in `appendImmutable`, which updates a card reply when the card answer changes, is not editing and stays. A correction is a new message. Stored rows keep their existing revisions and show as today; nothing is deleted. The edit journey (`neo-publication-edit-db`) and edit tests go with it, and the edit steps in `card-reply-daemon.ts` and `publication-open-target.ts` are dropped from those journeys. The verify seeds that call `edit()` directly (`preview-candidates.ts`, `preview-resolve.ts`, `wake-conversation-disclosure-seed.ts`) append a new publication instead.
6. **Remove the old path.** Delete the full session → front `message.send` route, `BACKGROUND_RESULT_NOTE` and its envelope, and the `dual_model_front_required` refusal. The envelope for messages from other sessions stays. Sweep the names the human sees or the front reads: `NEO_REFUSALS` (`front_ack_required` names the old tool; `front_not_speaking` and `front_model_required` say Convo) the failure text in `front-outcome.ts` ("Convo could not complete this reply"), `publication_superseded` (shared by the speaker, lifetime and claim gates; its "Edit the existing answer" clause goes, leaving "This input's session or conversation changed. Publish from the current live turn."), the front tool texts in `front-model.ts` that say "background result", the dual-model setting text in `en.ts` and `zh-Hans.ts` (and its `i18n.test.ts` assertion) and labels in `ModelsSettings.tsx`, which become "Fast replies: a quick model answers first and Neo does the work", and the session title `Convo` in `folder.ts` and `CONVO_TITLE` in `front-session.ts` (written at creation and on every input), which becomes `Neo fast replies`.

## Change

Closes #10467. Four PRs, in order, each from `dev`:

1. **Remove editing** (point 5). Deletion only.
2. **Catch-up block** (point 3) in `front-job.ts`: the tags, escaping, the 4 KiB cut, `publishedBy`, and the migration (`catch_up_from`, `catch_up_through`). Construction; harmless while the full session cannot publish.
3. **Two speakers** (point 2), with every instruction that describes the behavior, so prompts never contradict routing: `publication-operation.ts`, `neo-publication-repository.ts`, `service.ts` (speaker predicate, listening fan-out), `neo-front-input-worker.ts` (reserve and lane claim, `input_handed_off`, and the owner backfill migration), `front-model.ts` (atomic hand-off, wake note deleted), `front-outcome.ts`; and, still under the old tool name, the full session's dual-mode note and the front's "Only you speak" note in `front-mode.ts`, the relay detail on the publish refusal in `publication-operation.ts`, and the `run_in_background` description, which now says the answer goes to the human by itself. Wiring.
4. **One identity and the old path** (points 1, 4, 6): the rest of the prompts, the `work_on` rename, `front-model.ts` and `front-session.ts` (allowlist, `handoff_read`), `session-envelope.ts`, `message-send.ts`, `neo-refusals.ts`, the naming sweep, and the `neo-front-execution.ts` verify journey moved to the new path. Mostly deletion.

Tests: in dual mode the full session publishes and speaks directly; progress replies do not claim; the front cannot publish for an input the full session owns and gets `input_handed_off`; a card reply on an input the front owns is accepted with its card; the same lane can still send many updates and a later result for one input, including in a batch with an answered input; a crash during hand-off leaves the input either reserved and enqueued or neither; after the upgrade, an input answered before it by inferred owner refuses the other lane and accepts a same-ID retry; two queued front inputs get consecutive catch-up ranges; a redelivered input gets the same bytes after a card revision and after a listening change; the listening note reaches both sessions; a handed-off input settles as handed off with no extra message; a reservation that wins between settlement's owner read and its fallback append is requeued, settles as handed off, and the fallback still reaches the batch's unowned inputs; the front's next input starts with everything said since its last consumed input, and again after a failed delivery; a reply that mentions an answered card produces no re-confirmation; human, publication or quoted text containing `</human-message>` or `<said …>` arrives escaped; the first input after the migration carries no catch-up; switching modes changes no prompt text.
