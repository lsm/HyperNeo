# Native Learner worker and learning workflow

**Status:** Proposed implementation specification  
**Scope:** Continuous-learning gap #1, with the minimum PR-agnostic terminal contract needed by gap #2 and the proposal-validation data needed by gap #3  
**Parent:** Goal `#951beac9`; originating task `#895`; design task `#917`

## Decision summary

Add a seventh preset **worker** agent, `Learner` (`handle: learner`), and a built-in single-node **Learning Workflow** (`handle: learning-workflow`). The worker operates an existing goal-linked Forge scope directly. It is not a long-horizon actor and does not own goals, schedules, or Forge scopes; the goal and scope remain the durable steering state, while long-horizon actors may retain `owner`/`manager`/`watcher` assignments.

The workflow has one start/end node and no channels, PR hooks, review gate, or post-approval route. At autonomy level 2 or higher, the Learner records a terminal decision artifact and calls `approve_task`; the existing no-route completion path transitions `in_progress → approved → done`. Below level 2 it calls `submit_for_approval`; the resulting pending level-1 review bundle may be applied only by a verified human operator action, never by a coordinator or task-agent session. No task-level `requires_pr` or `no_code` flag is introduced.

Goal automation remains the trigger source. Its completed-task threshold, self-nag schedule, and external-event subscriptions create a task pinned to `learning-workflow`; they no longer run the episode judge and then create a generic review task. The Learner performs the whole Forge cycle in the workflow so evidence selection, episode review, proposal validation, lessons, metrics, and completion share one accountable execution trace.

## Verified current state

The design builds on these existing seams rather than replacing them:

- Forge already stores goal-linked scopes, evidence, episodes, findings, lessons, proposals, and metric snapshots (`packages/shared/src/types/evolution.ts:3-290`).
- Episode generation already loads evidence, related tasks and workflow runs, metric history, active/candidate lessons, and proposed/accepted proposals (`packages/daemon/src/lib/space/evolution-episode-service.ts:213-258`). The judge creates a draft episode with `outcomeSummary` and findings, plus candidate lessons and proposed tasks linked through `evidenceEpisodeIds` (`packages/daemon/src/lib/space/evolution-episode-service.ts:173-211`).
- Proposal materialization is already atomic and idempotent and creates a goal/scope-linked task (`packages/daemon/src/lib/space/evolution-episode-service.ts:327-391`).
- Space member sessions expose the native Forge MCP operations: scope resolution, evidence and metric reads/writes, episode generation, review bundles, lesson/proposal updates, proposal-to-task conversion, and goal rollup (`packages/daemon/src/lib/space/tools/space-agent-tools.ts:3838-4459`).
- Goal automation already supports three trigger kinds: completed-task threshold, self-nag cron, and external-event subscription (`packages/daemon/src/lib/space/goals/goal-automation-service.ts:45-180`). Today the job handler invokes the episode service itself and creates an unpinned `Review Evolution retrospective` task (`packages/daemon/src/lib/job-handlers/goal-automation-execute.handler.ts:82-207`, `:293-318`).
- Worker node sessions already receive both `node-agent` and space-scoped `agent-memory` MCP servers (`packages/daemon/src/lib/space/runtime/task-agent-manager.ts:999-1281`, `:5132-5141`). The memory repository is currently keyed by `(space_id, key)`, not agent identity (`packages/daemon/src/storage/repositories/agent-memory-repository.ts:89-138`, `:187-199`).
- Forge scope ownership is currently a long-horizon-agent relation (`owner | manager | watcher`), with assignment APIs accepting only long-horizon agents (`packages/daemon/src/storage/schema/long-horizon-agents.ts:53-67`, `packages/daemon/src/lib/space/tools/space-agent-tools.ts:1837-1867`).
- The task state machine already permits `in_progress → approved` and `approved → done` (`packages/daemon/src/lib/space/managers/space-task-manager.ts:32-74`). `approve_task` is gated by `workflow.completionAutonomyLevel` (`packages/daemon/src/lib/space/tools/end-node-handlers.ts:373-415`). When a workflow declares no post-approval route, the router closes `approved → done` directly and captures terminal Forge evidence (`packages/daemon/src/lib/space/runtime/post-approval-router.ts:302-390`).
- Existing Research and Review-Only workflows are not suitable substitutes: Research requires a PR-ready hook and post-approval merge; Review-Only instructs its terminal agent to post a GitHub review (`packages/daemon/src/lib/space/workflows/built-in-workflows.ts:794-965`).

## Agent definition

### Identity and lifecycle

Add this preset to `seed-agents.ts`:

| Field | Value |
|---|---|
| Name | `Learner` |
| Handle | `learner` |
| Family | Worker (`SpaceWorkerAgent`) |
| Description | Operates goal-linked Forge learning cycles: evidence → episode → validated lessons and proposals. |
| Tool profile | Learner-specific capability profile, enforced through filtered MCP servers |
| Default model/thinking | Inherit the Space defaults; no Learner-specific provider contract |

This is deliberately a **worker**, not a long-horizon agent:

1. A learning cycle is bounded execution with a clear terminal result, so it fits a workflow node.
2. Schedules and external subscriptions already persist in goal/Forge automation; a second always-on Learner session would duplicate trigger ownership.
3. Forge scope ownership currently belongs to long-horizon actors. Changing that relationship merely to run a workflow would conflate steering ownership with execution.

A long-horizon `Product Quality Manager`, Coordinator, or future domain owner may own/manage/watch the scope. The Learner receives `goalId`, `scopeId`, trigger context, and evidence cursor in its task and operates that scope for one cycle.

### Tool surface

The Learner needs the normal node terminal tools plus a **curated subset of the existing Space tools**. This is an enforced v1 capability boundary, not prompt guidance. An empty worker `toolProfile` is insufficient because `deriveWorkerDisallowedTools` only filters deniable built-ins and an empty profile leaves all Space MCP operations available (`packages/daemon/src/lib/space/agents/tool-policy.ts:22-31`). The Learner must use an **exhaustive built-in allowlist** containing only the read-only SDK tools required for reasoning; every built-in not on that allowlist is denied. At minimum, the resulting `disallowedTools` must include every repository or shell mutator (`Bash`, `Monitor`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`) **and** every agent-delegation and scheduling tool (`Agent`, `Task`, `Workflow`, `CronCreate`, `ScheduleWakeup`, `RemoteTrigger`). These names must be passed explicitly rather than merely omitted from a conventional worker profile—`DENIABLE_TOOLS` does not include all of them, and `MonitorInput.command` is a shell escape on providers that expose `Monitor`. The exhaustive complement rule also makes newly introduced built-ins denied by default until deliberately reviewed and allowlisted. Without this, the Learner could run a shell command through `Monitor`, spawn a `general-purpose` child that receives `Bash`, or create persistent follow-ups via `Workflow`/`CronCreate`/`ScheduleWakeup` that goal automation is supposed to own. A Learner never modifies the repository directly or through delegation—only through the filtered Space MCP surface.

Add a Learner-specific MCP provisioning path in `TaskAgentManager`: construct filtered `space-agent` and `node-agent` servers whose registered tool names are limited to the allowlist below, and provision a **filtered Learner memory server** in place of the ordinary `agent-memory` server. Do not attach the ordinary server: `createAgentMemoryMcpServer` registers unrestricted `memory.write` and `memory.delete`, which would defeat the enforced namespace below. The filtered Learner memory server exposes only the scope-derived prefix-enforcing `memory.write` wrapper described in the Memory namespace section, plus `memory.search`/`memory.read`, and omits deletion entirely.

This omission must survive the required-servers self-heal. `agent-memory` is on `requiredWorkflowSubSessionMcpServers()` (`task-agent-manager.ts:4899`), and `ensureNodeAgentAttached` (`:4923-4949`) calls `reinjectAgentMemoryMcpServer` (`:5114-5122`) on every spawn/rehydrate, which would otherwise re-inject the ordinary unfiltered `agent-memory` server before the first turn. Implement one of: (a) drop `'agent-memory'` from the required list for Learner sessions, or (b) make `reinjectAgentMemoryMcpServer` Learner-aware so it re-injects the filtered server. Either path must guarantee that after `ensureNodeAgentAttached` runs the session exposes the filtered server only (ordinary `memory.delete` absent).

The filtered server is also **scope-bound** to the current task's `evolutionScopeId` and `goalId`: every object lookup and mutation handler must resolve the target's scope and reject cross-scope or mismatched-goal access, even when the object belongs to the same Space. This applies to evidence, metrics, episodes, lessons, proposals, validations, materialization, review bundles, and rollup. Do not rely on IDs supplied by the prompt or agent; inject the authorized scope into the handler context and include it in repository queries. The workflow agent must not receive the unfiltered Space server in parallel. Learner provisioning must also **suppress all non-curated MCP sources**: globally enabled registry MCPs, skill-backed MCPs, and slot `extraMcpServers` are excluded for Learner sessions—only the filtered space-agent, filtered node-agent (Learner-aware `reinjectNodeAgentMcpServer` re-injects the filtered server, not the ordinary one), and filtered Learner-memory servers are attached. The effective MCP registry is enforced against the complete computed set on every spawn and rehydrate, so a Space with filesystem, Git, or other mutating MCPs enabled does not let the Learner bypass the capability boundary. Unknown/new Space tools therefore remain denied until deliberately added to this profile.

The filtered servers must omit scope creation/relinking, agent-assignment, generic task creation, and every other Space mutation not listed above. A learning run may report `missing_scope` or request an owner decision, but it cannot silently change the steering topology. Prompt instructions remain defense in depth, not the authorization mechanism.

### Memory namespace

The current memory store is shared by every session in a Space, so the design must not claim storage-level per-agent isolation that does not exist. For the first implementation, enforce a **logical namespace**:

```text
learner/<scope-id>/<slug>
```

Every Learner-written key must use that prefix and tags must include `learner`, `forge`, and `scope:<scope-id>`. Enforce this in a Learner-specific memory wrapper that derives the prefix from the task-bound scope, rejects caller-supplied keys outside it, and adds the required tags server-side. Do not expose ordinary `memory.write` or any memory deletion operation to Learner in v1; deletion remains unavailable until storage-level ownership exists. Search/read may still surface shared Space memories and are not an authorization boundary. Store only operational heuristics not already represented by Forge rows—for example, source-specific metric collection instructions or a correction to evidence interpretation. Episodes, findings, proposal outcomes, and lessons remain in Forge and must not be duplicated into memory.

A follow-up may add repository-enforced owner namespaces. Until then, the enforced write wrapper prevents cross-namespace mutation, while the UI/background consolidation may still surface these memories to other agents.

## Workflow definition

```ts
export const LEARNING_WORKFLOW: SpaceWorkflow = {
  id: '',
  spaceId: '',
  name: 'Learning Workflow',
  handle: 'learning-workflow',
  description: 'Single-node Forge learning cycle with a PR-agnostic terminal.',
  templateSlug: 'learning-workflow',
  nodes: [
    {
      id: 'tpl-learning-learn',
      name: 'Learn',
      agents: [
        {
          agentId: 'Learner',
          name: 'learner',
          customPrompt: { value: LEARNER_WORKFLOW_PROMPT },
        },
      ],
    },
  ],
  startNodeId: 'tpl-learning-learn',
  endNodeId: 'tpl-learning-learn',
  tags: ['learning', 'forge'],
  channels: [],
  hooks: [],
  gates: [],
  completionAutonomyLevel: 2,
  createdAt: 0,
  updatedAt: 0,
};
```

Critical absences are part of the contract:

- no `postApproval` route;
- no `pr_ready` hook;
- no GitHub review gate;
- no peer channel or reviewer node;
- no PR-specific artifact requirement.

`completionAutonomyLevel: 2` matches the risk of producing internal evidence, lessons, proposals, and draft/accepted follow-up work. Creating an execution task from a proposal remains separately visible and auditable.

Level 1 must not perform those durable mutations and then merely submit the already-mutated result for approval. Enforce a shared `requireLearningMutationAutonomy` check in the mutation handlers used by this workflow—episode accept/dismiss, lesson activation/dismissal, proposal acceptance/dismissal, proposal-validation finalization/reset/reopen, and goal rollup, **and every content edit** (`update_forge_episode`, `update_forge_lesson`, `update_forge_task_proposal`) to a row that is already in a terminal disposition (`accepted`, `dismissed`, `active`, `created`). Content-only edits to an accepted/abandoned episode or active/retired lesson (evidence IDs, findings, rule, rationale) would otherwise bypass the review bundle and rewrite the historical basis of existing validations, so a terminal row that grounds a dependent is **immutable at every autonomy level**—not merely below level 2. Correction is only via audited replacement/versioning (create a successor row and supersede), never an in-place content edit. The terminal set includes `accepted`, `dismissed`, `abandoned`, `active`, `retired`, and `created`—and abandonment is irreversible (a row marked `abandoned` can never return to `draft`). Only candidate/proposed/draft rows remain editable to prepare the bundle. Once an episode disposition (`accepted`/`dismissed`/`abandoned`) grounds a dependent row—an active lesson, accepted proposal, or final validation—it is fully immutable (status and content); `update_forge_episode` rejects any status transition that would invalidate those dependents (e.g. flipping an accepted episode to `dismissed` after it grounds a final validation), so committed Forge rows cannot be retroactively un-grounded. The check evaluates the **pinned `cycleAutonomyMode`** (see step 6), not a live re-read of Space autonomy, so a mid-cycle lowering cannot strand the run. It permits draft evidence, metric snapshots, draft episode/proposal creation, and **pending** proposal-validation creation needed to prepare a review bundle, but requires level 2 before changing review dispositions, finalizing a validation verdict, or changing goal state, and rejects content edits to grounded terminal rows at every level (audited versioning only). At level 1, the Learner persists each complete expected/measured/proposed-verdict triple as a validation with `status: 'pending'`, saves a decision artifact whose `pending_validation_ids` and recommendation reference those rows, leaves all generated lessons/proposals in candidate/proposed state, and calls `submit_for_approval`. The `submit_for_approval` terminal handler—not a separate Learner-callable mutation—atomically validates that the artifact contains an exhaustive disposition for every episode, candidate lesson, proposed task, **every cycle-owned `pending` and `staged` validation** (each appearing exactly once—matching the autonomous terminal check, so a `staged` reopen successor cannot be omitted and orphaned), and the complete proposed rollup payload, then copies that immutable recommendation into a cycle-level `learning_review_bundle` row keyed by `(taskId, revision)` with `status: 'pending'`—even when there are no proposal validations. It rejects missing, duplicate, unknown, or unaccounted-for object IDs rather than inferring recommendations from mutable Forge state. The bundle also stores, for every referenced Forge row, an immutable reviewed snapshot: the accepted/proposed content plus a version/`updatedAt` precondition (or content hash) for each episode, lesson, proposal, validation, metric snapshot, and rollup target. The task stores the current revision; retry of the same submission is idempotent. The authorized human review action is a dedicated, operator-verified surface—**not** the existing `approve_pending_completion` MCP path, which remains exposed to coordinator and legacy task-agent sessions and is therefore unsafe for learning-bundle application. The handler requires a verified human/operator authorization context and stamps the true actor; an AI coordinator applying the bundle is rejected. Apply atomically finalizes the bundle's dispositions in **dependency order within the transaction**—episode accept/dismiss, then lesson activation and proposal acceptance, then validation finalize/reject/reopen, then rollup—validating each handler's preconditions against the bundle's projected final state rather than the start-of-transaction state, so a normal bundle that accepts an episode and then finalizes a validation referencing it is not wrongly rejected. Apply first re-reads each referenced row and rejects the apply if any row's version/hash differs from the bundle's reviewed snapshot, so an intervening edit cannot substitute different content for what the human reviewed. A `stale_reviewed_version` failure terminalizes that attempt (`status: 'stale'`) **and** increments the task's bundle revision in the same transaction before returning the task to `in_progress`, so a corrected `submit_for_approval` creates a new pending revision with refreshed snapshots instead of reusing the stale idempotency key and failing forever. Explicit human rejection likewise marks the revision `rejected`, increments the revision, and returns the task to `in_progress`. Both transitions atomically reject that revision's pending validations **and terminalize every `staged` successor owned by that revision** (`status: 'rejected'`, recorded in the supersede chain) before the revision is terminalized—since a bundle may reference validations from its own revision only and only one current pending/final row may exist, the next revision cannot reuse or replace them unless they are first rejected, and a lingering staged successor would otherwise let each corrected revision fork another audit chain toward the same predecessor. A corrected resubmission then creates replacement validations under the new attempt key. Only the current revision may be applied. Successful verified-operator apply is the level-1 terminal transaction: after applying the reviewed Forge dispositions, it atomically marks the bundle `applied`, validates and commits the artifact/cursor/continuation and `nonTriggeringForGoalAutomation` stamp, completes the workflow run, transitions `review → approved → done` through the no-route completion path, and releases the active-cycle lease when no continuation reservation remains. Retry after a crash is idempotent on `(taskId, revision)` and a reconciler completes any `applied` bundle whose task/run terminal writes were not committed; ordinary task approval cannot close the run or advance its cursor before this transaction. Thus the gate covers every level-1 cycle rather than depending on a nonempty `pending_validation_ids` list. Rejecting the checkpoint therefore leaves no accepted lesson, accepted proposal, final validation verdict, or goal rollup to undo. As with task materialization, tool visibility is optional UX and handler enforcement is the authorization boundary.

### Terminal artifact

Before terminal action, save one decision artifact. Both learning terminal handlers enforce it: `submit_for_approval` validates the current cycle artifact before creating a review bundle, and `approve_task` validates the same artifact and its task/scope/episode references, **mirrors `submit_for_approval`'s exhaustive requirement that every cycle-owned episode, lesson, proposal, validation, and rollup has a terminal disposition** (no draft episodes left uncommitted), and requires every cycle-owned `pending`/`staged` validation to be finalized or rejected—**except** rows tracked as `pendingReopen` (staged successors whose reopen boundary has not yet been observed), which are exempt from the terminal check so the first-phase reopen task can close without discarding its staged successor. before any run status, cursor, or continuation write—so an autonomous cycle cannot reach `done` and advance its evidence cursor while leaving a proposal-wide-current pending row that blocks later validation. Missing, failed, stale, or inconsistent artifacts (or unresolved validations) leave the task `in_progress` with a structured error. This invariant also belongs in the **central task status-transition service**, not only the terminal MCP handlers: for a task pinned to `templateSlug: 'learning-workflow'`, every attempted transition into `done` from `in_progress`, `review`, `approved`, or `blocked` is rejected unless it is executed inside the dedicated autonomous or verified-operator terminal transaction with a validated artifact, committed cursor/continuation state, and server-stamped `nonTriggeringForGoalAutomation`. Generic `spaceTask.update`, recovery, archival, and internal callers cannot bypass that guard:

## Trigger wiring

### One trigger service, one execution path

Retain the existing policy and trigger recognition:

- threshold: `GoalAutomationService.onTaskCompleted`, with each completed-task occurrence first written to a durable trigger outbox;
- schedule: `onSelfNag` plus existing schedule reconciliation, with each occurrence first written to a durable trigger outbox. Because `selfNagCronExpression` is optional in `GoalForgeAutomationPolicy`, acceptance of a proposal with a schedulable window schedules a **boundary-observation job** at the computed due point (not a separately dispatchable validation occurrence); the observer creates and fences the validation occurrence atomically with its result, so validation never runs before measurements settle and the same window is never delivered twice. Anchor resolution (freezing the timestamp in the acceptance snapshot) and `reset-verification` (installing a new current snapshot) **atomically cancel the old occurrence and boundary-observation job and re-arm new ones at the updated due point** (`min(anchorTimestamp + durationMs, absoluteDeadline)`), so measurement always happens at the correct boundary even when the anchor resolves to an earlier time than the fallback. Recognition must not return `not_applicable` solely because `selectEvidenceAfterCursor` is empty: it also enqueues when any proposal in scope has a closed verification window awaiting validation or any metric definition is observable, since the observation pre-check at step 1.7 is what makes such a cycle productive. The verification window is machine-readable: `verificationMethod.window` carries a `startAnchor` (`acceptance` | `taskCreation` | `taskCompletion`), a `durationMs` and/or `absoluteDeadline`, and optional `completionPredicate`; the due point is computed deterministically as the **earlier** of `startAnchorTimestamp + durationMs` and `absoluteDeadline` (when both are present), where the anchor timestamp is read from the acceptance snapshot's `acceptedAt`, the materialized task's `createdAt`, or its `completedAt` respectively; a task-anchored window whose task has not yet been materialized (or completed) uses its required acceptance-measured `absoluteDeadline` fallback so it is never skipped indefinitely. Once a task anchor resolves (materialization or completion), the timestamp is **frozen** in the active acceptance-snapshot version along with a monotonic `completionVersion` stamped at that moment. If the fallback `absoluteDeadline` passes while the anchor is still unresolved, the snapshot is atomically fenced as `fallbackResolved` (the anchor is treated as unresolved at that boundary and the verdict is non-effective); a later task completion cannot retroactively resolve the anchor and change the verdict. `onSelfNag` queries proposals in scope with an acceptance snapshot whose computed due point has passed and that have no current `final` validation **and no pending boundary-observation job and no outstanding/fenced validation occurrence** for the current snapshot/window (a proposal whose boundary observer is still running, retrying, or has already emitted its fenced occurrence is excluded from self-nag dispatch, preventing redundant cycles)—covering both `accepted` and materialized `created` proposals, since `createTaskFromProposal` transitions a proposal to `created` and those materialized interventions are the most likely to need post-task validation—so it can neither suppress validation indefinitely nor validate before the intervention has run. When the fallback deadline fires on a task-anchored proposal whose task was never created, or whose `taskCompletion` anchor never completed, the verdict must be **`unavailable`** (not `ineffective`) unless the acceptance snapshot already binds immutable application evidence proving the intervention ran. This prevents authorization/non-execution outcomes from poisoning future learning with a false caution lesson. A `taskCreation` anchor is accepted only when the snapshot binds that immutable application-evidence ID (for example, a deployment artifact) and freezes its application timestamp; once present, later queued/cancelled task execution does **not** trigger the non-execution override, and the boundary measurement can yield `effective` or `ineffective`. Without such evidence, the proposal must use `taskCompletion`; a queued/cancelled task then finalizes `unavailable`.
- external: `onExternalEventPublished` with cursor-based deduplication, persisting each occurrence to a durable trigger outbox atomically with its evidence and dedup-marker update.

Change only the queued job's terminal action. `handleGoalAutomationExecute` should stop calling `episodeService.createFromEvidence` and stop creating a generic review task. Instead it creates one learning task with:

- `goalId` and `evolutionScopeId` set;
- `preferredWorkflowId` resolved by the built-in workflow's **canonical template identity** (`templateSlug: 'learning-workflow'`), not by display name or handle. An existing Space may already contain a user workflow named `Learning Workflow` or using handle `learning-workflow`; `createWorkflow` rejects duplicates on those unique fields, and resolving by handle could fail or select the unrelated custom workflow—bypassing the secured Learner node and filtered MCP provisioning. The built-in seed carries a collision-safe `templateSlug` (`learning-workflow`) as a concrete database column (added by the storage migration with `UNIQUE(space_id, template_slug)` scoped uniqueness), distinct from its display name/handle. Because `createWorkflow` still enforces name and handle uniqueness, the migration does not rely on the colliding fields: on a collision it derives **unique display fields in a checked loop** (trying `Learning Workflow (Forge)`/`learning-workflow-forge`, then incrementing a suffix until both name and handle are free) while stamping the canonical `templateSlug`, so creation always succeeds and automation resolves `preferredWorkflowId` by `templateSlug` regardless of the display fields. Because workflow runs already pin an immutable creation-time definition (`definition-version.ts`), the canonical hash/topology validation runs **only at dispatch** against the mutable head. At dispatch the automation therefore also validates an **expected template hash and canonical Learner-only topology** (exactly one `Learn` node, no extra nodes/routes/agent slots, no `postApproval` route), **rejects a disabled template** (a disabled Learning Workflow must not fall back to another workflow for a system-pinned learning task), and refuses to dispatch on mismatch. **Task creation and every spawn (initial and rehydrate) validate only the reservation's pinned definition**—no head revalidation occurs after dispatch. The pinned-definition validation on spawn covers both initial spawn and rehydrate consistently.
- labels `['forge', 'learning', 'automation', <trigger-token>]`;
- structured metadata or a stable description containing all merged trigger contexts, cursor boundary, external event IDs when present, and candidate evidence IDs;
- a deterministic automation-cycle lineage key scoped to `(goalId, evolutionScopeId)` so retries and concurrent trigger kinds do not create duplicate tasks.

The task is the durable unit of work. Goal automation must serialize cycles at the goal/scope level, not separately by trigger kind. In one transaction, acquire the active-cycle lease for `(goalId, evolutionScopeId)`, merge trigger contexts into its durable pending set, claim evidence while reserving a `triggerEvidenceBudget`, persist the **validated workflow+agent identity** (template hash, presetSlug, pinned definition version) with the reservation so task creation uses that pinned version (not a re-validation against a potentially edited head), and reserve the initial task ID plus a task-creation outbox row. If the pinned definition is later found invalid during task creation (e.g. deleted entirely), the task-creation outbox records a terminal failure that returns the claim and releases the lease. The dispatcher materializes that reserved task idempotently. A startup/periodic reconciler repairs every leased cycle with a reservation but no task/outbox delivery; triggers coalesced during the gap cannot strand the scope. Release the lease only when no **non-terminal** task remains—terminality is derived as any status in `{done, cancelled, archived}`; all other statuses hold the lease—plus no pending review bundle or live task-creation/continuation reservation. **Scheduled proposal-observation outbox rows are excluded from the lease condition**: they are durable background jobs that must persist without holding the active-cycle lease, so a future verification window does not block intervening automation.

For self-nag, the schedule-fire transaction must insert a unique occurrence into the trigger outbox **before/with** `updateAfterFireIfPending`; delivery merges that occurrence into the goal/scope lease idempotently. Advancing the cron schedule is therefore not acknowledgement of trigger delivery, and reconciliation retries undelivered occurrences after crashes or enqueue failures.

The same durability applies to completed-task thresholding. The terminal handlers currently invoke `GoalAutomationService.onTaskCompleted` synchronously and only log failures (`end-node-handlers.ts:203-211`, `post-approval-router.ts:376-383`, `space-task-handlers.ts:640-648`). Insert the completed-task occurrence into the trigger outbox **with** the task's `done` transition and its durable `task_result` evidence (the occurrence stays pending until the evidence capture is confirmed), and let the goal/scope dispatcher merge it into the lease idempotently rather than firing inline. The dispatcher **applies the threshold count before merging a learning trigger**—at `completedTaskThreshold > 1`, completions accumulate until the threshold is reached, then a single learning cycle is triggered. A reconciler scans durable completed-task evidence whose threshold occurrence was never delivered and re-enqueues it, so a capture/queue failure after the task is already `done`—especially at threshold 1 with no later task—cannot permanently lose the learning cycle.

External events need the same treatment. `onExternalEventPublished` must, in one transaction, create/idempotently resolve the Forge evidence, write a unique external-event occurrence to the trigger outbox, and advance the source-dedup marker; the goal/scope dispatcher then merges that occurrence into the lease idempotently. A crash after the dedup marker advances but before the occurrence is merged cannot drop the trigger: the reconciler re-delivers outbox occurrences whose lease merge is absent, preserving event-specific provenance without relying on a redelivery.

Use one canonical evidence cursor per `(goalId, evolutionScopeId)` for episode selection. Before enabling the new dispatcher, migrate existing evidence deterministically to append sequences ordered by `(created_at, id)`. For each scope, derive the safely processed prefix primarily from evidence linked to terminal accepted/dismissed episodes **proven to originate from legacy automation** (for example, episodes whose source task was queued by the legacy goal-automation handler)—never from manually reviewed episodes, which by contract do not consume automation evidence. Proven-processed evidence counts as processed **independently of stale per-trigger cursors**: do not cap the boundary at the oldest legacy cursor when a terminal automation episode proves later evidence was already processed (e.g., a completed-task run that accepted evidence 1–12 while an older self-nag cursor sat at 4 must seed through 12, not 4). Use legacy per-trigger cursor ranges only to identify additional ambiguous pending evidence, not to shrink a proven-processed prefix. Where a **terminal** episode's origin is ambiguous (manual vs. legacy automation, or unverifiable), leave its evidence pending rather than advancing the boundary over it. Before exposing that pending evidence to native dispatch, separately detect taskless legacy **draft graphs** created in the crash window after `createFromEvidence` but before the legacy review-task transaction: a draft episode with generated candidate lessons/proposals, no source review task/terminal disposition, and evidence matching a legacy automation claim is atomically marked `abandoned`, its candidate lessons dismissed and proposals marked `dismissed` with `orphaned_legacy_draft`, and its evidence left pending for replay. If provenance proves the draft belongs to a recoverable legacy review task, adopt/link it instead; never leave the old graph live while replaying its evidence into a native episode. Seed the canonical cursor only through the contiguous prefix proven processed; **persist every proven evidence ID—including noncontiguous trigger-evidence IDs linked to a terminal accepted/dismissed legacy episode—as processed in the gap-aware set**, so the native dispatcher does not reclaim already-committed trigger evidence. Persist only genuinely ambiguous intervals (not proven processed by any terminal episode) as explicit pending ranges/IDs, so migration neither replays committed episodes nor skips divergent legacy windows—nor silently skips evidence that only a manual run ever touched. Run this migration and invariant check transactionally before automation resumes.

Trigger-kind cursors remain only source-delivery dedup markers (for example, the last external event received); they never determine the Forge evidence window. On accepting an external-event publication, atomically create/idempotently resolve its Forge evidence **before** advancing the source-dedup marker or merging its trigger context, and order that evidence by an append-time Forge sequence rather than backdated `externalEvent.ingestedAt`. Store the external event ID as the uniqueness key and its ingestion time as metadata only. A delayed job therefore references evidence already positioned after the canonical boundary; legacy late evidence detected at or behind the boundary goes into the durable pending-trigger queue as an explicit claimed evidence ID and is processed without moving the cursor backward. When acquiring the lease, atomically read the global processed boundary, merge all pending trigger contexts, and claim the next contiguous evidence prefix. Terminal handling advances only this global cursor through the committed prefix. This prevents an older self-nag cursor from replaying evidence already processed for an external event and prevents a newer source cursor from skipping evidence unseen by another source. The Learner selects the claimed evidence (bounded by `maxEvidencePerEpisode`) and runs the judge.

Learning-workflow task completion is terminal evidence but must be marked `nonTriggeringForGoalAutomation` as a concrete server-stamped boolean persisted on the learning task and its completion-outbox record atomically with the `done` transition, so both normal delivery and durable reconciliation honor the exclusion. The filter must compare the workflow's canonical `templateSlug === 'learning-workflow'`—**not** its handle. The collision-safe seeding may give the built-in workflow a non-`learning-workflow` handle when a user workflow already owns that handle, so a handle check would either fail to exclude the built-in completion (recursive scheduling at threshold 1) or wrongly suppress the user workflow. The completion may remain visible in the Forge timeline, but it neither increments `completedTaskThreshold` nor recursively schedules another learning cycle.

Each trigger context carries a monotonically assigned pending-trigger sequence. The cycle's evidence claim records the greatest trigger sequence it covers. Terminal handling must reserve a continuation whenever **any** merged context—completed-task, self-nag, or external-event—has a later sequence or an explicit evidence ID not covered by the committed claim. It releases the goal/scope lease only when every pending context is covered or durably reserved for a continuation; no trigger kind depends on another notification to drain.

### Cursor semantics

Do **not** advance the automation cursor when the task is merely created. Advance it only after the learning workflow reaches `done`. The cursor remains a contiguous processed-prefix boundary: a completed cycle may advance it only through the greatest evidence position for which every preceding item is either included in that episode or explicitly recorded as examined and deferred to a durable next-cycle queue. It must never jump directly to the greatest selected evidence ID, because forcing trigger evidence beyond `maxEvidencePerEpisode` could otherwise strand the skipped prefix. A dismissed episode still counts as examined; a failed or human-rejected run does not advance the cursor—except that abandonment reconciliation of already-committed effects advances through the examined subset (evidence that grounded the committed episode/lesson/proposal) while still returning unexamined evidence to the pending set. An `abandoned` draft episode (see below) does **not** count as examined—its evidence stays pending so a replacement can re-claim it; this is why `abandoned` is a distinct terminal status, not a reuse of `dismissed`. Extend `EvolutionEpisodeStatus` from `'draft' | 'accepted' | 'dismissed'` to include `'abandoned'`, and add it to the schema CHECK (`evolution.ts:60-61`) and the Zod enum (`space-agent-tools.ts:5411`), mirroring how this spec adds `retired` to `ProposalValidationStatus`.

An abandoned learning task (cancelled or archived before `done`) must release its goal/scope lease without losing the work it had claimed—and without duplicating work it has already committed, and without resuming business side effects the user just stopped. Prefer staging all gated cycle mutations (episode accept/dismiss, lesson activation, rollup, materialization) into the single terminal transaction so a pre-terminal abandonment has committed nothing to duplicate or resume. If the implementation mutates incrementally instead, cancellation reconciles **only already-committed state** (records it, advances the processed set through evidence that committed tail actually examined, and deduplicates via cycle-key/snapshot invariants) and **splits the claim**: the examined subset is committed (processed) and the **unexamined remainder plus any uncovered merged trigger contexts are atomically returned to the pending-trigger set** so they are not stranded—while uncommitted business effects (rollup, materialization, further dispositions) stay cancelled (no auto-resume). Only a cycle with no committed effect may requeue its full frozen claim.

The draft-graph retirement applies to **every** abandonment with an uncommitted draft graph, not only review cancellations. `create_forge_episode` persists a `draft` episode plus `candidate` lessons and `proposed` task-proposals before any disposition, so a level-2+ task cancelled while still `in_progress` (after that call but before accept/dismiss), or a level-1 task cancelled in `review`, both leave that durable draft graph behind. The abandonment transition must, in the same transaction, retire it—mark the draft episode `abandoned` (the non-examined terminal status above), dismiss its candidate lessons, and reject its candidate proposals (audit-preserved)—or transfer/reuse the original cycle key to the replacement so the `(scope_id, cycle_key)` uniqueness suppresses the duplicate graph directly. It must also reject every `pending` and `staged` validation owned by that cycle, regardless of autonomy level or review state (candidate task proposals are set to `dismissed` with audit reason `abandoned_cycle`, since `TaskProposalStatus` does not include `rejected`), and **cancel or fence any boundary-observation job and undelivered occurrence** owned by a rejected staged reopen successor—otherwise the job can later fire for an already-rejected successor after a replacement cycle has begun: an autonomous level-2+ task cancelled after `create_forge_proposal_validation` but before finalize/reject otherwise leaves an orphaned proposal-wide-current `pending` row that blocks a replacement from creating another validation (the validating episode is `abandoned` and can never ground finalization). Without this, a replacement under a new cycle key would duplicate the draft graph or be blocked by stale validations. If the task is additionally in `review` (level-1 pending bundle), the same transition first atomically rejects the current pending bundle revision and its pending validations—otherwise the lease contract's "pending bundle keeps the lease active" rule leaves the scope leased forever. The reconciler scans completed cycles missing terminal markers and leased cycles whose task is terminal-abandoned, classifies which case applies, and re-dispatches or finalizes accordingly, so an abandoned window is neither permanently occupying the scope, silently dropped, nor duplicated.

Abandoned learning tasks must not be retried through the generic `retry_task` path, which currently permits `cancelled` workflow tasks and reopens them (`space-agent-tools.ts:2510-2528`): retrying the original after a replacement was reserved would run two tasks over the same evidence with no lease owner. The same restriction covers **completed** (`done`) learning tasks and **every recovery path**, not just `retry_task`: `VALID_SPACE_TASK_TRANSITIONS` permits `cancelled → in_progress` and `done → in_progress`, and `spaceTask.update` routes workflow recovery through `recoverWorkflowBackedTask`. The Learner-specific guard must live in that central recovery/status-transition path—either `recoverWorkflowBackedTask` refuses to restore a terminal learning-workflow task, or every recovery atomically reclaims the goal/scope lease, invalidates the prior terminal artifact, and establishes a new cycle identity before restoring the run.

The trigger evidence must therefore be selected together with prefix evidence up to the cap. If the trigger lies beyond the cap, persist it on a durable next-cycle queue as priority evidence rather than appending it across a gap. Terminal completion must commit the task's `done` transition, contiguous cursor update, and durable continuation-outbox row in one database transaction whenever that queue remains nonempty. An outbox dispatcher creates the continuation learning task with the advanced cursor boundary and deferred trigger context, using the same deterministic lineage key plus a monotonically increasing cycle sequence; idempotent consumption prevents duplicates. A startup/periodic reconciler scans completed learning cycles whose cursor/outbox terminal marker is absent and transactionally repairs it, closing the crash gap even if a legacy/non-transactional terminal path is encountered. The continuation does not depend on another external event, threshold notification, or self-nag tick. Continue chaining bounded prefix cycles until the deferred trigger is consumed and the queue is empty. The implementation may instead introduce a gap-aware cursor with explicit pending ranges, but a scalar cursor is valid only with this prefix-extension-and-continuation rule.

While a cycle for the same `(goal, scope)` is `open`, `in_progress`, `review`, `approved`, `blocked`, `rate_limited`, or `usage_limited`, coalesce every trigger kind into that task or its pending-trigger set. A pending level-1 review bundle, reserved continuation task ID, or unconsumed continuation-outbox row also holds the same goal/scope lease and counts as an active cycle. The terminal transaction reserves the continuation task identity before marking the predecessor done; a live notification during outbox dispatch merges into that reservation rather than creating a competing task. Preserve the existing completed-task active-lock/requeue behavior until this durable lease replaces the process-local lock.

### Manual runs

A user or long-horizon owner can create a task explicitly pinned to `learning-workflow`. This is not started through the generic `create_standalone_task` surface, which cannot set the system-owned `goalId`/`evolutionScopeId`; instead define a **verified manual learning-task creation operation** that resolves the goal/Forge scope, persists both bindings on the task, acquires the manual-mode lease atomically, and **applies the same canonical-template validation and no-fallback rule** as the automation dispatcher (validates the resolved workflow's template hash, topology, and enabled status; refuses to create under a disabled or modified template).—`cycleAutonomyMode` is left unset at creation and stamped at the first gated mutation (matching the general pinning rule at step 6), so a queued manual task does not inherit a stale elevated mode if autonomy is lowered before execution begins. Scope relinking (`UpdateEvolutionScopeParams.spaceGoalId`) must acquire the same goal/scope lease (or be rejected while a learning lease holds the scope), and **must also be rejected while scheduled proposal boundary-observation jobs exist** for that scope—relinking would strand the old job against a scope that no longer belongs to its recorded goal. If relinking is required, it must atomically cancel every affected observation job and migrate snapshots/validations first. This is not a fourth automation trigger kind; it is ordinary workflow execution and records a single `manual` entry in the artifact's `triggers[]` array, with a task-local `key: 'task:<task-id>'` and `sequence: 0` (no automation trigger key, no dedup cursor metadata). Manual runs have no automation trigger key or cursor boundary and never read, advance, or enqueue continuations for automation cursors; their selected evidence is linked to the manual episode without consuming it from any later automated window. They are still scope mutations, however: a manual run must acquire (or wait on) the same goal/scope mutation lease used by automated cycles **before its first Forge write**—not only before dispositions—because observation, episode creation, candidate generation, and pending-validation creation already persist scope state that could race a concurrent automated cycle. The relevant tool handlers verify the caller holds the manual-mode lease before any such write. The lease is acquired in a distinct manual mode that does not advance or block the canonical automation cursor, so a concurrent automated cycle and a manual run at autonomy ≥ 2 cannot both create competing draft graphs, validation rows, or dispositions for the same episodes, lessons, proposals, validations, or goal rollup. This serialization must hold for **every** Forge writer, not only the Learner: the shared Forge mutation services (episode, lesson, proposal, validation, metric, rollup) enforce the active goal/scope lease for any caller—coordinator, long-horizon agent, or Space member using the unfiltered tools—rejecting a mutation that conflicts with a held lease. Two system-owned paths are exempt (like the boundary observer): trigger-evidence ingestion (external-event publication appends its Forge evidence and outbox occurrence through a trusted system path without granting ordinary callers lease-bypass authority), completed-task evidence capture (`captureCompletedTaskEvidence` after `done` transition), and boundary observation (defined above). the autonomous Learner path additionally passes a version/content-hash precondition on each row it finalizes (optimistic concurrency), so an intervening unfiltered edit cannot slip between the Learner's read and its finalize.

## Learner procedure

The workflow prompt must instruct the agent to execute this procedure, not merely describe the architecture.

### 1. Resolve and bound the cycle

1. Read the task, goal, and supplied trigger context.
2. Resolve `scopeId` from the task and verify it belongs to the goal.
3. Read scope policy, metric definitions, timeline, evidence after the supplied cursor, prior metric snapshots, candidate/active lessons, and open/created proposals.
4. Recall only scope-relevant Learner memory.
5. Attach any missing task/workflow-run evidence referenced by the trigger, and atomically extend the frozen cycle claim to include exactly those rows. This runs **before** the empty-claim check so a trigger whose only evidence is a missing referenced row is never silently marked covered. The dispatcher reserves a `triggerEvidenceBudget` out of `maxEvidencePerEpisode` at claim time for these attachments; the exact-match episode check validates the union of reserved prefix evidence plus attached trigger rows, which must remain ≤ `maxEvidencePerEpisode`. If the prefix already fills the cap and a newly attached trigger row would exceed it, the handler defers that attached row (and its trigger context) to a continuation rather than extending a full claim—never omit it and never exceed the cap.

   Attachments must not create a noncontiguous processed set. A newly attached row receives an append sequence at the tail of the evidence log, so if the scope has a backlog beyond the reserved prefix the attachment would land at, say, position 101 while the prefix is 1–8—and a scalar cursor advanced through 8 would either reprocess 101 later or strand 9–100. Therefore the canonical processed boundary is a **gap-aware set** (processed evidence IDs plus explicit pending ranges), not a scalar. A cycle that includes an out-of-prefix trigger attachment records those IDs as claimed ranges in that set and terminalizes them as examined; intervening unprocessed ranges remain pending. The implementation may use a scalar cursor only for cycles whose processed set is genuinely contiguous; any attachment beyond the contiguous prefix requires the gap-aware representation so no evidence is reprocessed or stranded.
6. Select a coherent evidence cluster from the reserved prefix, capped by `maxEvidencePerEpisode`, while preserving a contiguous cursor prefix. Prioritize trigger evidence within that prefix; if it lies beyond the cap, durably defer it to the next cycle rather than skipping intervening evidence. The reserved prefix may contain evidence from multiple unrelated threads; selecting a coherent subset requires an **atomic claim-narrowing** operation (`narrow_forge_cycle_claim`) that rewrites the frozen claim down to the selected subset and returns every omitted reserved ID to the pending set (gap-aware, re-processable by a later cycle). The narrowed claim is a **contiguous cursor prefix plus zero or more explicit claimed attachment ranges** (the same gap-aware shape the full claim uses). When two coalesced trigger contexts attach unrelated evidence that both fit the cap, the Learner may pick one coherent cluster and `narrow_forge_cycle_claim` atomically returns the omitted trigger attachment IDs **together with their trigger contexts** to a continuation (rather than forcing every attachment into one incoherent episode), so the retained cluster stays coherent and the deferred trigger is processed by its own later cycle. The narrowed claim must still include any trigger attachment not deferred this way. `create_forge_episode` then exact-matches the narrowed claim. Using the whole un-narrowed claim would contaminate the episode with unrelated threads; submitting the subset without narrowing would fail `evidence_claim_conflict`. The dispatcher's full claim is the capacity ceiling, not the mandatory episode input.
7. Before declaring the claim empty, run the observation pre-checks: capture any due metric snapshot (a scheduled self-nag often fires precisely when a verification window has elapsed, with no new preexisting evidence), and identify earlier proposals whose verification window has now closed or whose outcome is otherwise measurable (due validations). The cycle is **not** no-op if any of these holds, even when the pre-existing evidence claim is empty—the freshly captured snapshot is attached via the observation claim-extension path and the due proposal proceeds to validation. When a due validation's metric threshold result is an *absence* (the boundary measurement exists but does not meet the threshold, or the readiness predicate is false), the server-grounded boundary observation itself serves as the evidence row—the captured metric snapshot proves the measured value, and the cycle finalizes `ineffective` without requiring additional evidence. For v1 (threshold-only mode) this path is always reachable; event/test verification modes are future work. Only when there is no new evidence, no observable metric, and no due validation may the Learner record a no-op decision artifact and complete without creating an empty episode; this prevents scheduled cycles from repeatedly reporting `no_op` while an awaited proposal never gets validated.

### 2. Observe and measure

Observation steps create new evidence (metric snapshots create both a snapshot and a Forge evidence row; manual notes append evidence). These run after the claim is frozen, so each such creation uses the same authorized claim-extension path as trigger attachments: the handler reserves an `observationEvidenceBudget` (distinct from the trigger budget, sized in scope policy, default small) at claim time and atomically extends the claim with the new row, or—if the union would exceed the cap—defers that observation to the next cycle without consuming it in the current episode (the snapshot is still persisted as standalone metric data). Observation evidence appended beyond the contiguous prefix is subject to the same gap-aware processed-set rule as trigger attachments—it is recorded as a claimed range, never allowed to strand or reprocess intervening evidence. The exact-match episode check therefore never rejects observation evidence as `evidence_claim_conflict`, and the canonical cursor does not reprocess an observation already used by a validation/artifact.

1. Capture a **before/after or current** metric snapshot when metric definitions have observable values. For a due-validation cycle the verdict and readiness predicate must use an observation **at the due boundary**, never a backdated post-window value: the scheduler enqueues a **server-grounded boundary observation** at the due time—a server job reads **every metric referenced by `threshold.metricKey` and by every `completionPredicate` operand** via their registered collectors (resolved from the snapshotted metric-definition bindings, not the current registration), passing the **fixed boundary timestamp** to each collector so it returns a historical value at that point if supported. Collectors that do not support historical reads must be queried at the boundary; if the job is delayed, the retry passes the same boundary timestamp and the collector either returns the persisted due-time value or the job finalizes `unavailable` for that metric—**never** accepts a later current value as the boundary result. Captures all values and `captured_at` authoritatively as one fenced set (one retry outcome for the complete set), and writes the snapshots through a **trusted boundary-observer lease path**: the observation write is exempt from the agent-held goal/scope lease conflict check (it does not grant the agent unrelated mutation authority), so a lease held at the deadline does not delay or block the boundary capture. The boundary-observation job **enqueues the validation occurrence on success or retry-exhaustion**—the due-validation occurrence does not fire independently of the observation settling, so validation always has measurements (or a fenced `unavailable` result from the exhausted retry) when it runs. Metrics without a registered server-readable collector cannot be used in a threshold verification and the proposal is rejected at acceptance. If no boundary snapshot exists and the metric source lacks a trustworthy historical query, the cycle records an **`unavailable`** verdict (terminal, not deferred): the shared service derives `unavailable` only after persisted retry state (`retryDeadline`, `retryCount`) on the **boundary-observation outbox row** (the durable job record that schedules the server capture) expires with no trustworthy boundary measurement. The finalizer reads and atomically fences that record. Add `MetricDefinition.valueType`, `collector`, and a monotonic `revision` field to the shared type (`evolution.ts:65-72`) with a conservative migration; the `revision` increments whenever `valueType`, `unit`, or `collector` changes, so the snapshotted `version` in `metricDefinitionSnapshots` can be populated and audited from the source model. Numeric thresholds require `valueType: 'number'`. Persist the boundary result so a later re-run does not re-evaluate.
2. If a metric cannot be measured, record why in evidence rather than inventing a value.
3. Identify earlier proposals whose created tasks or expected verification windows are now represented in the evidence.

### 3. Create one episode

Call `create_forge_episode` with the selected evidence and a required `cycleKey` derived from the workflow task/run. Add `cycle_key` to episodes with a unique `(scope_id, cycle_key)` constraint, and make `createFromEvidence` an idempotent get-or-create transaction: a retry returns the existing episode and its already-created findings/lessons/proposals rather than invoking the judge or inserting children again. The handler must not trust the evidence IDs supplied by the model on the first call: inject the server-validated evidence claim into the handler and require an **exact set match** (same IDs, no omissions, no out-of-window extras) before the initial judge transaction; a mismatch fails with `evidence_claim_conflict` and the canonical cursor is never advanced. For automated cycles the claim is the server-reserved goal/scope lease claim (prefix evidence plus trigger attachments). For **manual** cycles there is no automation lease, so the Learner-built selection is committed as a task-local manual claim through a dedicated server-validated manual creation path: the handler validates the supplied set against `maxEvidencePerEpisode` (rejecting an oversized claim rather than letting an unbounded payload reach the judge), records the bounded evidence set against the task once, then enforces exact-match against that recorded manual claim on retry—manual evidence is never consumed from any automation window. Reuse checks compare against the recorded claim, not against whatever the first call happened to persist. On resume, the Learner first reads the review bundle/episode by cycle key and continues from its persisted state. The existing judge produces the draft episode, findings, candidate lessons, and candidate proposals only on the first insertion. Do not recreate these objects manually unless correcting a specific judge omission.

Bound metric history before invoking the judge. `buildEpisodeInput` currently calls `listMetricSnapshots(scope.id)` unbounded (`evolution-episode-service.ts:224`), so a long-running recurring scope serializes its entire accumulated history into every prompt and cost grows with scope lifetime. The implementation must pass an evidence/validation window plus a bounded baseline (for example the earliest and most-recent N snapshots per metric) to the judge, never the full history—keeping prompt size and cost bounded regardless of scope age.

Review the generated bundle for:

- evidence grounding and cross-scope contamination;
- duplicate lessons/proposals;
- consistency with existing active lessons;
- result-artifact gaps already detected by the service;
- proposals missing required expected outcome or verification method.

Update `episode.outcomeSummary` if needed, then accept or dismiss the episode. Activate only evidence-backed lessons whose every causal `evidenceEpisodeId` is **accepted and belongs to the lesson's own goal/Forge scope**—the shared lesson create/update/activate service (not only the Learner wrapper) enforces both, so an unfiltered caller cannot ground an active lesson on a cross-scope accepted episode; a lesson linked to a dismissed episode cannot be activated, and a level-1 bundle may not pair episode-dismiss with lesson-activate. Dismiss duplicates or unsupported candidates.

### 4. Form proposals

Every proposal must include:

- **Expected outcome:** the observable change if the proposal works;
- **Verification method:** a registered numeric metric collector with a structured threshold (`{metricKey, op, value, unit?}`) and a schedulable window (`{startAnchor, durationMs/absoluteDeadline}`); test/event comparison modes are future work and should not be generated for v1;
- evidence episode links;
- a bounded action description and priority.

A proposal without both fields remains `proposed` and cannot be accepted or materialized into a task. Acceptance (and task materialization) additionally requires every one of the proposal's causal `evidenceEpisodeIds` to be **accepted**: a proposal generated from a dismissed episode cannot be accepted or materialized, since the cycle has declared its evidence unusable. The accept and materialize handlers enforce this, and a level-1 bundle may not pair an episode-dismiss disposition with acceptance of a proposal linked to that episode.

Use a one-high-confidence-proposal-per-cycle default to limit self-generated work. Additional candidates may remain proposed for later review. Proposal acceptance and task materialization are distinct authorities: level 2 may accept a proposal, but `create_task_from_forge_proposal` requires both Space autonomy level 3 or higher **and** `scope.policy.automation.createTasksFromAcceptedProposals === true`, plus the existing no-duplicate/idempotency checks.

Enforce this in the `create_task_from_forge_proposal` MCP handler (or a shared evolution scope-policy service called by it), before `episodeService.createTaskFromProposal`. The autonomy leg uses the cycle's pinned `cycleAutonomyMode` when a learning-cycle context exists; a non-Learner caller falls back to current effective Space autonomy. The scope opt-in leg always reads current `scope.policy.automation.createTasksFromAcceptedProposals`. Return a structured authorization error when either condition is absent.

**Materialization vs. elapsed-fallback:** this recovery applies only to an accepted proposal that has **never created a task** but whose acceptance-fallback `absoluteDeadline` elapsed or whose pre-execution validation already finalized `unavailable`. Ordinary `create_task_from_forge_proposal` rejects that stale acceptance window; the only valid path for the same proposal is `reset_and_materialize`—a single atomic operation that requires level 3 + scope opt-in, rejects while a staged reopen successor exists (or atomically cancels it), verifies `createdTaskId === null` and that the existing final verdict (if any) is `unavailable`, fences any pending boundary observation, retires that final verdict without producing a lesson, creates a new versioned acceptance snapshot with a schedulable task-anchored window, and creates the proposal's first task in one transaction. There is no separate pre-reset call or ordinary materialization fallback for this never-materialized case. A proposal with an existing `createdTaskId` can never be materialized again or have its task lineage reset; a genuinely new intervention requires a fresh proposal linked as a successor. Anchor resolution and `reset_and_materialize` both atomically cancel the old boundary job and re-arm at the new due point.

### 5. Validate earlier proposals

For each earlier proposal whose outcome is now measurable, create a validation record with an explicit triple:

```text
expected: <original expected outcome and threshold>
measured: <metric/evidence value, window, and source>
verdict: effective | ineffective | superseded | unavailable
```

Verdict rules:

- `effective`: the boundary measurement of `threshold.metricKey` meets the predeclared threshold (and the readiness `completionPredicate`, if any, is true);
- `ineffective`: the verification window closed without the threshold being met, or the readiness predicate is false (an unresolved task anchor at the fallback deadline finalizes as `unavailable`, NOT `ineffective`—it was never executed, so it cannot be recorded as a failed experiment);
- `superseded`: the intervention or target was replaced so the original causal claim is no longer testable; identify the replacement proposal/task.

The verdict is determined **solely** by `threshold.metricKey` and the readiness predicate against the boundary measurement—there is no separate "regressions outweigh the gain" override. **Non-execution override:** if the intervention never ran (task was queued/cancelled, or the anchor never resolved), the deterministic finalizer overrides the threshold result to `unavailable` regardless of any ambient measurement, preventing a false `effective`/`ineffective` and misleading lesson. If regressions must affect the verdict, encode them in the immutable verification contract (e.g. additional `threshold.metricKey` gates via the predicate) at acceptance; the freeform regression language is removed.

Never rewrite the original expectation after observing results. Link the validation to the originating proposal, its created task when present, the validating episode, and metric snapshots. Finalization requires its validating episode to be **accepted**: an episode dismissed in the same cycle for weak or contaminated evidence cannot ground an effective/ineffective verdict or activate a lesson. The finalize handler enforces this; a validation linked to a dismissed episode must remain rejected/deferred, and a level-1 bundle may not pair an episode-dismiss disposition with a validation `finalize`. When a due proposal's validating episode is dismissed, the rejection persists a durable **deferral** on the proposal—concrete persisted fields (`deferredUntil: number`, `deferredAfterEvidenceSeq: number`, and a relevance predicate over evidence kinds)—and `onSelfNag` excludes that proposal until `deferredUntil` elapses AND evidence with a sequence beyond `deferredAfterEvidenceSeq` matching the relevance predicate arrives (deterministic wake-up across restarts). The deferral transition persists a **durable recheck occurrence** at `deferredUntil`, so the proposal is guaranteed a wake-up even in a scope without a self-nag cron or later trigger. The occurrence is not consumed if the AND condition is false (it persists as a durable waiter); when matching post-deadline evidence later arrives, that evidence append enqueues/upserts the validation occurrence so both conditions are satisfied., so every later schedule does not regenerate a due observation and a re-dismissed episode for the same unchanged result.

Each completed validation produces or updates a lesson only when its verdict yields a reusable rule:

- effective → activate a rule describing what to repeat and under which conditions;
- ineffective → activate a caution describing what not to repeat and why;
- superseded → activate only when the replacement itself yields a reusable rule; otherwise retain the validation without forcing a lesson;
- unavailable → complete the validation with `lessonId: null`; missing execution or exhausted measurement retries provide no causal rule to preserve.

If no suitable candidate lesson exists, call `create_forge_lesson` with the validation-derived rule, `status: 'candidate'`, and links to the validating episode/proposal, then activate it only after the same level-2 disposition gate. Validation creation must not silently synthesize an active lesson because lesson review and validation finalization remain independently auditable.

### 6. Roll up and finish

1. Apply a concise goal rollup only when the episode is accepted **and** the goal type is `recurring`: summary, metric deltas, and next steps. The rollup service must require `episode.status === 'accepted'` (rejecting `draft`, `dismissed`, and `abandoned` explicitly—not just `dismissed`—so neither an unreviewed draft nor an explicitly non-examined abandoned episode can mutate the goal), and reject every non-recurring goal. The current rollup service also strips `progress` before calling the goal service (`evolution-episode-service.ts:409-410`); `SpaceGoalService.updateGoal` independently deletes progress for recurring goals (`goal-service.ts:151-157`). Do **not** set `rollup.progress` until a dedicated recurring-progress mechanism exists in the goal service; record evidence-backed progress as a metric snapshot and in the terminal artifact's `rollup.metric_deltas` (matching the validated schema) instead, so the field is never silently dropped. For an accepted `one_shot` or `measurable` goal, preserve the learning result in Forge and the terminal artifact but leave goal state unchanged; any later support for those goal types belongs in the goal service rather than this workflow. For a dismissed episode, preserve the dismissal reason and likewise leave goal state unchanged. In every path, advance the cursor only under the contiguous-prefix rule above.
2. Write only non-Forge operational heuristics to `learner/<scope-id>/...` memory.
3. Save the terminal learning-cycle artifact.
4. Call `approve_task` as the final action; if autonomy blocks it, call `submit_for_approval` instead.

Autonomy must be pinned for the whole cycle. Persist `cycleAutonomyMode` as an **immutable, server-stamped task/run field** (added by the storage migration) stamped at the **first gated mutation** (not at task creation): if the Space autonomy is lowered while the task is still queued (before any gated effect), the task re-evaluates the current level at that first mutation and stamps it then. If the session was spawned before the first mutation and the pinned mode differs from what the session was told, the terminal handler uses the pinned mode for the artifact and rejects a session-prompt/terminal-action mismatch rather than creating an unnecessary review bundle. Once stamped it is immutable for the rest of the cycle. This prevents a queued task from inheriting a stale elevated mode while still pinning genuinely mid-cycle runs. Use it consistently in every mutation and terminal handler for that cycle. If the Space autonomy is lowered after the Learner has already passed the level-2/3 gates, `approve_task`/`submit_for_approval` and every disposition handler still use the pinned mode, so the run cannot strand itself with half-applied Forge rows, a half-updated goal, or follow-up tasks that a later rejection cannot undo. This includes the runtime contract the agent actually sees: `TaskAgentManager.buildNodeExecutionRuntimeContract` currently recomputes the live Space level and instructs the end-node agent that `approve_task` is unavailable and it must call `submit_for_approval`—for learning tasks it must instead derive terminal-tool availability and the rehydrated end-node prompt from `cycleAutonomyMode`, so a level-2-pinned Learner is told to `approve_task` even if the Space was just lowered to 1 and does not enter a level-1 review path whose bundle cannot represent its pre-applied effects. (Equivalently, stage all gated mutations and commit them in one atomic terminal transaction.) The pinned mode is recorded in the terminal artifact.

Uniqueness is enforced at two levels: `(proposal_id, validating_episode_id, attempt_key)` for the full row, and a **partial unique constraint** `UNIQUE(proposal_id, scope_id) WHERE status IN ('pending', 'final')` (excluding `staged`) so the database itself prevents two current attempts from coexisting even under concurrent inserts. `attemptKey` is a per-cycle attempt revision that exists on both paths: for level-1 cycles it equals the bundle revision (`bundleRevision` non-null); for autonomous (level ≥ 2) cycles there is no review bundle, so `bundleRevision` is null and `attemptKey` is the cycle/episode attempt sequence—giving autonomous validations a defined, queryable revision without inventing bundle semantics. A rejected validation is immutable; corrected resubmission creates the next attempt with `supersedesValidationId` pointing to it, preserving the audit chain. `supersedesValidationId` is the backward link on a later validation; the forward/audit link is `reopenedByValidationId` on the retired row. `reopen_forge_proposal_validation` is defined **exclusively as the atomic replacement operation**: in one transaction it stages the successor and **establishes a new versioned acceptance snapshot with a new schedulable window and re-arms the due-validation schedule and boundary-observation job at the new boundary**. The predecessor stays current until the new boundary observation fences; only then does a second atomic transaction retire the predecessor, promote the successor, and finalize it—so the successor is never finalized from pre-window or stale data. There is no standalone "retire-first, finalize-later" form: the predecessor stays current until the successor is committed atomically, so a crash can never leave the proposal with no current verdict. `supersedesValidationId` is reserved strictly for the retry/audit chain (a corrected attempt pointing at its rejected predecessor); the reopen-predecessor relationship is expressed exclusively through `reopenedFinalValidationId`/`reopenedByValidationId`, so the two links are never overloaded. Only one **current** (pending or final) validation may exist per proposal—uniqueness is proposal-wide, not scoped to the proposal/episode pair. When one validation becomes `final`, the handler atomically rejects every sibling pending row for that proposal so none lingers as a stale candidate. Every `pending` row must belong to a recoverable lease/attempt (the creating caller's goal/scope lease and attempt key): the shared creation service stamps the immutable `ownerLeaseId`/`ownerTaskId` (provenance) and the `currentOwnerLeaseId`/`currentOwnerTaskId` (authoritative current owner), and a stale-cleanup reconciler rejects pending rows whose `currentOwnerLeaseId` lease is gone or whose `currentOwnerTaskId` attempt has been terminal-abandoned. Orphan adoption is an audited ownership transfer: it updates `currentOwnerLeaseId`/`currentOwnerTaskId` to the adopting cycle (preserving `ownerLeaseId`/`ownerTaskId` as immutable provenance). The sole exception is a **staged successor** paired with a reopen: a bundle (or autonomous reopen call) may create a new `pending` validation whose `reopenedFinalValidationId` points at the still-current `final` row (its `supersedesValidationId` stays null unless it is also a corrected retry), marked `staged` (non-current) so it does not violate proposal-wide uniqueness. The staged row's `validatingEpisodeId` is **nullable** (it is populated when the future cycle creates its episode); `measured` and `verdict` are also nullable for staged rows. The terminal handler's exhaustive no-staged-validation check exempts rows whose reopen has not yet reached its boundary observation (they are tracked as `pendingReopen` rather than `staged` in the handler's state, so the reopening task can close without being blocked). **At most one staged successor per `reopenedFinalValidationId`** (partial unique constraint on `reopenedFinalValidationId WHERE status = 'staged'`); reopen retries return or replace the existing successor rather than creating a second. The staged snapshot is **not** promoted to `currentSnapshotVersion` until the successor is successfully finalized; on rejection, `currentSnapshotVersion` is repointed to the predecessor's version while preserving the staged snapshot for audit. This resolves the level-1 ordering hazard—the Learner's first bundle contains only a `reopen_stage` disposition; the verified-operator apply authorizes staging (creates the successor + new window). A later observation-backed cycle creates the validating episode and records a second bundle with `finalize` or `reject` for the successor, which the operator applies. The old one-bundle path (recording both `reopen` and `finalize`/`reject` simultaneously) is removed because it would decide the successor's verdict before the authoritative boundary observation exists. if the bundle recommends `reject` for the successor (e.g. its validating episode was dismissed), the predecessor stays `final` and its lesson untouched—the attempted revalidation simply fails closed—so the proposal never loses its current verdict because of a rejected successor. A bundle may reference validations from its own revision only, with two explicit exceptions **per staged successor**: (1) the predecessor `final` validation that a given staged successor reopens, identified by that successor's `reopenedFinalValidationId`; (2) **the staged successor itself** across revisions: the later observation-backed cycle's bundle may reference the staged successor by its immutable `attemptKey` and adopt it for finalize/reject, because the first-phase task that created the successor has closed and the successor now belongs to the scope's pending state rather than any single task revision. a reopen bundle may also reference the predecessor `final` validation that a given staged successor reopens, identified by that successor's `reopenedFinalValidationId` (distinct from `supersedesValidationId`, which carries the retry/audit chain—e.g. a rejected earlier attempt—so a corrected attempt after a rejected staged successor can point its `supersedesValidationId` at the rejected attempt while its `reopenedFinalValidationId` points at the still-current final, satisfying both requirements). The handler permits one such cross-revision predecessor reference per staged successor—so a cycle revalidating several finalized proposals can stage several successors, each pointing at its own predecessor—and rejects any other cross-revision reference. Finality is **proposal-wide**: once a proposal has a current `final` validation, no second final row may be created for it from a later episode—the proposal's declared verification window is consumed. Longitudinal revalidation is supported through an explicit audited `reopen_forge_proposal_validation` operation—the atomic replacement defined above—which is the only legal way to retire a current `final` **except** for the audited `reset-verification` transition (defined in the materialization section), which is the one explicit exception: it atomically retires the current final and installs a new schedulable window, leaving the proposal with no current verdict until the new window produces one—this is legal because the proposal's verification contract itself changed. Reopen atomically retires the prior verdict's `lessonId` **only when no other current `final` validation still references that lesson**—two final validations may legitimately share or update one active lesson, and unconditionally retiring it would retroactively violate the other verdict's active-lesson requirement. Retirement is a real supersession, not an unrelated dismissal: extend the lesson model with a `supersededByLessonId` forward link (and `supersedesLessonId` back link) plus a `retired` status, added as concrete columns by a storage migration, and the lesson handler records the link so the audit relationship reopen relies on is queryable rather than silently folded into `dismissed`. If the successor reuses the predecessor's existing lesson (same `lessonId`)—confirming it unchanged—the atomic replacement special-cases the identical ID: it leaves that lesson active and writes no self-supersession link. The finalizer's evidence-episode requirement is relaxed for reused lessons: a reused `lessonId` is accepted if the predecessor's episode is in `evidenceEpisodeIds` (the predecessor episode was already accepted), rather than requiring the successor's new `validatingEpisodeId`—since reusing an unchanged active lesson means the successor confirms the same rule, not derives a new one from a new episode. If the rule is being *updated*, the successor must instead create (or version) a **distinct** successor lesson and supersede the old one—never rewrite the shared active lesson in place, since that would silently change the rule recorded by the predecessor and any other validation sharing the ID. When the replacement is a `superseded` verdict that carries no successor lesson (`lessonId` null), the old lesson **stays active**—`supersededByLessonId` is nullable and only set when a successor lesson exists—so the audit contract is not violated by a missing successor. Independently, the lesson handler rejects any `dismiss`/`retire` of a lesson while a current `final` validation still references it, except inside the atomic replacement path, so an ordinary `update_forge_lesson` cannot strand a final verdict without its required active lesson. If another final validation still references it, only the retirement of that shared old lesson is blocked; the replacement validation must still finalize with its own **distinct** active lesson immediately (not deferred), so longitudinal revalidation is not gated on an independent verdict ever being retired. Autonomous (level ≥ 2) Learners invoke reopen through the filtered MCP allowlist, following the **same two-phase protocol** defined above: stage the successor and new window first, then retire/promote/finalize only after the new boundary observation fences—never a bare retire-then-finalize. A level-1 cycle instead records a `reopen_stage` disposition requesting first-phase staging; operator apply authorizes that staging (creates the successor + new window), and a later observation-backed cycle chooses and applies the terminal disposition (finalize/reject). Add create/list/finalize/reject/**reopen** service operations (reopen is autonomy-gated like finalize); include validations in `list_forge_review_bundle` and the judge prompt. This prevents conflicting `effective`/`ineffective` verdicts and contradictory lessons while keeping longitudinal revalidation achievable. Exactly one of `replacementProposalId` or `replacementTaskId` may be set for a superseded verdict; both are null otherwise. Each must reference an object linked to the same goal/Forge scope as the validation; `replacementProposalId` must differ from the validated proposal, be in an `accepted` or materialized (`created`) state, and carry a server-stamped `replacesProposalId` lineage edge (same as the task relation) proving it causally replaces the validated proposal—not merely same-scope and accepted. `replacementTaskId` must differ from the validated proposal's own `createdTaskId`, reference a task in state **`done`** bound to an **immutable completion occurrence** (the `done` transition stamps a monotonic `completionVersion` that the validation references; the central recovery guard refuses to recover any completed task while it is referenced by a final validation), and carry an immutable server-stamped causal-replacement relation: the task must have a persisted `replacesProposalId` stamped by a **server-side `link_replacement_task` operation** (autonomy-gated, called before the replacement task reaches `done`) or an equivalent `proposal_replacement_lineage` table entry. The finalization service also rejects any `replacementProposalId` that would create a cycle: walk the validated proposal A's existing predecessor chain (following `replacesProposalId` links from A backward) and reject if it reaches the candidate B; equivalently, check whether traversal from A after inserting B→A returns to B. A direct B→A replacement is always accepted when A's chain does not contain B; only genuine cycles (A→B and B→A, or longer loops) are rejected. and the **finalization service itself** (not only the Learner's filtered wrapper) validates that relation for both `replacementTaskId` and `replacementProposalId`—rejecting an unrelated cross-scope caller/object so the causal chain cannot be corrupted. Likewise the shared create/finalize service verifies that the validation's primary causal links—`proposalId`, `validatingEpisodeId`, and every `metricSnapshotIds` entry—all belong to the validation's goal/scope, so an unfiltered caller cannot ground a validation from another scope's accepted episode or measurements. For every verdict the service derives `expected` from the bound acceptance-snapshot version's `expectedOutcome` (no caller-supplied `expected` is persisted for any verdict, including `superseded`). The service also derives the complete structured `measured` object from the authoritative boundary-observation job and its referenced metric snapshot—callers supply neither measurement prose nor numeric fields—and verifies metric key/unit/timestamp linkage before finalization. If the authoritative job exhausts retries without a trustworthy snapshot, it records that terminal observation failure and finalizes `unavailable` with `measured: null`; `measured` is required for `effective`/`ineffective` and may be absent only for `staged` or final `unavailable` rows. For `effective`/`ineffective` the service **derives the verdict itself** by evaluating the readiness `completionPredicate` and the `threshold.metricKey` comparison against that persisted measurement, so neither an unfiltered caller nor an inconsistent Learner can finalize `effective` when the accepted threshold actually failed. `lessonId` is **required** (non-null) when finalizing an `effective` or `ineffective` verdict—the reusable rule is the point of the cycle; it stays nullable only for `superseded` and `unavailable` verdicts (neither yields a reusable rule). ## PR-agnostic completion

No core task flag is needed. The workflow declares its execution contract structurally:

1. `endNodeId` points to `Learn`;
2. the end node receives terminal tools;
3. the workflow has no PR hook/gate and no `postApproval` route;
4. `completionAutonomyLevel` governs self-close versus human approval;
5. the terminal artifact is a generic `decision`, not a PR link.

This is already PR-agnostic behavior. The implementation should add a regression test for this built-in workflow so future coding-specific validation cannot leak back into core completion.

## Open owner decisions

1. **One proposal per cycle:** Recommendation: default maximum one newly accepted/materialized proposal, configurable in scope policy; unlimited candidate proposals may remain `proposed`.
2. **Memory isolation timing:** Is the logical `learner/<scope-id>/` namespace sufficient for N1, or must repository-enforced agent ownership land first? Recommendation: ship logical namespacing with an explicit non-security warning; make enforced namespaces a separate migration.
3. **Superseded lessons:** Recommendation: do not force every superseded validation into a lesson; only create one when the replacement yields a reusable rule.
4. **Automation migration:** Existing pending automation review tasks should finish on their pinned/current workflow; only newly queued cycles use `learning-workflow`. Do not rewrite active tasks in place. To preserve serialization across the cutover, the upgrade migration must seed the new goal/scope lease with the **complete set of active legacy automation review tasks** for each affected scope (the old trigger-kind locking permits several—e.g. a self-nag and an external-event run—on one scope) and release it only after **all** of them have terminalized and reconciled; releasing per-task would let the first release unblock a native cycle while another legacy reviewer is still active. On reaching terminal status, each task's share is released in the **same** transaction that reconciles its legacy episode into the canonical cursor/pending-range state: advance the contiguous processed prefix through evidence linked to the accepted/dismissed episode, or record those IDs as examined/deferred. A **cancelled/archived/done** legacy review whose episode is still `draft` (the state machine permits `done` without accepting or dismissing) is not covered by that accepted/dismissed reconciliation, so the migration also defines a terminal-legacy transition that retires the draft graph (episode `abandoned`, candidate lessons dismissed, candidate proposals rejected, owned validations rejected) and leaves its evidence pending before releasing that task's lease share—otherwise the native dispatcher reclaims the same evidence while the legacy draft graph remains, producing the duplicate episode the lease was meant to prevent. Releasing the lease without this reconciliation lets the next native cycle reclaim the same evidence and generate a duplicate episode.

## Conclusion

The missing component is not another Forge store or another always-on coordinator. It is a bounded native execution path that lets a purpose-built worker use the stores already present, close without GitHub ceremony, and explicitly test whether prior proposals worked. The single-node Learning Workflow supplies that path while preserving the separation of Steering (goal), Learning (Forge), and Execution (workflow).
