# Neo route classifier evaluation (October 2026)

Evaluation behind [#5710](https://github.com/lsm/HyperNeo/issues/5710). It asks which model should decide
where a new message to Neo goes — an existing topic, `main`, or `inbox` — and whether the
richer input proposed in #5708 fixes the misroute that started it ("how about 5060 now?", a
follow-up to a PR question, sent to the inbox).

## Methodology

### The decision

Given the conversation so far and a new user message, pick one destination: a topic id, `main`
(main Neo, the default) or `inbox` (self-contained one-offs). Rules, as given to every candidate:

1. A message that continues a recent turn goes to that turn's topic.
2. An answer to a WAITING question goes to that topic.
3. A standalone message goes to the matching topic, to `inbox` if it is a one-off, or to `main`
   if it starts a new subject.
4. If unsure, or if more than one topic is waiting, choose `main`.

### Inputs

Two input shapes:

- **Message only** — the classifier input before #5714: the new message plus each topic's title
  and summary, rendered by the production `buildNeoRoutePrompt` as of `dev` 7939a6f1a. #5714
  has since moved production to routing context; the harness keeps the pre-#5714 prompt as
  this baseline (#5721).
- **Context** — the #5708 layout, built by `scripts/neo-route-eval/context.ts`:
  1. topics: id, title, summary (240 chars), latest exchange (`you: ask → answer`), and a
     `WAITING: asked you "…"` line when the topic asked a question;
  2. recent turns, newest first, as `[topic · 1h ago] you: <ask> → <answer>`, until 3,000
     characters;
  3. the new message.

LLMs get the context as a prompt ending in "Reply with exactly one id". Decision models get the
same text as `state` in a `/v1/systemone` request with one Choice question whose criteria are
the topic ids plus `inbox` and `main` — the TypeSafe Jev request format, which Kev, llama.cpp and
Cloudflare Clef also accept.

### Cases

105 cases, every one run through every candidate.

| kind | n | what it tests | expected |
|---|---|---|---|
| follow_up | 12 | "how about now?", "book it", an hour to a day after a turn | that turn's topic (`main` if the turn was in main) |
| second_last | 8 | refers to the topic before the latest one | that older topic |
| waiting_yes | 8 | "yes", "好的", "no, the later train" to one WAITING question, next day | the waiting topic |
| two_waiting | 6 | bare "yes" with two topics waiting; 2 disambiguated ("yes to the ryokan") | `main`; the named topic |
| one_off | 8 | "what is 15% of 2,340?", "what does HTTP 429 mean?" | `inbox` |
| new_subject | 8 | "let's plan the team offsite for March" | `main` |
| thanks | 6 | "thanks!", "谢谢", "ty" after a turn | that turn's topic or `main` |
| long_dictated | 6 | 400–700-char dictated asks with the question at the end | the topic, or `main` |
| mixed_language | 8 | mixed Chinese and English | as for the underlying kind |
| real | 35 | every ask in the tts Neo conversation, 2026-10-03 → 10-06 | hand-labelled |

- **Synthetic** (70): five fictional topics (a PR, a GPU build, a Kyoto trip, tax prep, a blog
  post) plus background turns 44–60 hours old. Generated by `synthetic.ts`; committed in
  `scripts/neo-route-eval/cases/synthetic.json`.
- **Real** (35): built by `build-real.ts` from a copy of four tables (`neo_conversation_asks`,
  `neo_publications`, `neo_routing_log`, `neo_concerns`) exported read-only from the tts daemon
  DB — the live 37 GB file was never written. Each ask was labelled with the destination it
  should have had; turns before it carry the gold topic of their own ask, as the router would
  have recorded it. Topic summaries are the concerns' current ones. The cases, labels and
  message text stay out of git; in `results/` the five real concern ids are replaced by
  `real-topic-1` … `real-topic-5`.
- A case can accept more than one answer (for example `thanks` accepts the topic or `main`).
- `followUp` marks cases whose message continues something; **follow-ups → inbox** counts those
  sent to `inbox` when `inbox` was not acceptable — the bug being fixed.

### Candidates and machines

| machine | hardware | ran |
|---|---|---|
| MacBook | Apple M5 Pro, 48 GB | Haiku 4.5 via the Agent SDK; Kev via MLX |
| tts (iMac) | Intel i9-10910 (20 threads), 72 GB, no GPU usable for this | GLM, DeepSeek, luna-6 via the Agent SDK, Codex bridge or native API; Kev via llama.cpp CPU |
| ai0 | Linux, RTX 2070 SUPER 8 GB (≈3 GB held by an ASR service) | Kev via llama.cpp CUDA; GLiNER2.5-Decide and Laya via `adapters/encoder_server.py` |

Every run is listed with its exact command in [`runs.md`](runs.md).

**Reasoning off.** Every model runs with reasoning off or at its minimum:

- Haiku 4.5: `thinking: disabled`.
- luna-6: `reasoning.effort: none`, forced on the Codex bridge's upstream request.
- DeepSeek Flash: `thinking: disabled`, injected by a local proxy.
- GLM-5-Turbo: thinking disabled through Zhipu's native API.
- GLM-5.3-Flash: `reasoning_effort: low`, the lowest it accepts.

The SDK GLM rows ran with thinking on and are labelled so; see [Findings](#findings).

**"Deployed" vs "lean".** For the Agent SDK path, "deployed" mirrors the production classifier
call. "Lean" adds three things: `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, an empty temporary `cwd`,
and a one-line system prompt.

### Metrics

- **Accuracy** — share of cases whose prediction is in the accepted set, overall, synthetic,
  real, and per kind.
- **Follow-ups → inbox** — as above, out of 74 follow-up cases.
- **Latency** — wall clock per route from the harness, p50 / p95, after 2–3 warm-up calls.
  - Agent SDK rows include spawning the CLI subprocess.
  - ai0 rows were driven from the MacBook over Tailscale (a few ms per call).
  - Native GLM rows are direct HTTPS.
- **Accuracy with 4 s timeout** — production gives up after 4 s and routes to `main`; this
  column applies that.
- **Cost per 1,000 routes** — measured input, cached-input and output tokens × official list
  price (table in [Caveats](#caveats)). Local models count as $0.

## Findings

1. **The misroute comes from the input, not the model.** With the message alone, every LLM sends
   follow-ups to the inbox: Haiku 31 of 74, the rest 5–21. With the #5708 context, every LLM drops
   to 0 (luna-6: 2) and gains 15–40 points. The real "how about 5060 now?" case (`real-35`) reproduces the bug: every message-only run
   misroutes it, 7 of 8 to `inbox`. Every LLM given the context routes it correctly.
2. **The Agent SDK's CLI injects the user's auto-memory into every classifier call.** A capture
   server in front of the CLI showed each request carrying `MEMORY.md` (≈8.8k characters) and the
   git environment, even with `settingSources: []`. A two-word prompt cost 3,040 input tokens.
   With `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` and an empty `cwd` it cost ≈320, and a full route
   dropped from ≈3,900 to ≈1,220. The SDK's own system prompt is small; the cost was the memory
   and git context.
3. **The CLI drops `thinking` for non-Claude models.** For a model id it doesn't recognise as
   Claude, it omits `thinking` and sends `output_config: {effort: "high"}`. Results:
   - GLM-5.3-Flash and DeepSeek Flash reasoned before answering, 28–272 output tokens for a single
     id.
   - `CLAUDE_CODE_DISABLE_THINKING=1` and `MAX_THINKING_TOKENS=0` change nothing.
   - `CLAUDE_CODE_EFFORT_LEVEL=low` only lowers the effort.
4. **Zhipu's Anthropic-compatible endpoint ignores `thinking: disabled`.**
   - GLM-5-Turbo returned thinking blocks with or without it; through a proxy injecting it, 47 of
     105 routes still reasoned.
   - GLM-5.3-Flash did on 66 of 105.
   - Zhipu's native `/api/paas/v4/chat/completions` honors `thinking: {type: "disabled"}` for
     GLM-5-Turbo (2 output tokens, 0 reasoning).
   - GLM-5.3-Flash refuses to disable at all ("always thinks; use low, high or max"), so
     `reasoning_effort: "low"` is its floor.
   - DeepSeek's Anthropic endpoint does honor `thinking: disabled` (at most 8 output tokens).
5. **The Codex bridge sends no reasoning effort when thinking is disabled,** so `gpt-5.6-luna`
   ran at its default effort until the harness forced `reasoning.effort: "none"` upstream.
6. **GLM-5-Turbo needs its thinking to be accurate here.** It scored 94% with thinking (Agent SDK,
   lean) and 87% without (native API). Without thinking it is also slow: native p95 5.3 s, past
   the 4 s timeout, so 74% after timeouts.
7. **Kev-4B is the best model on real asks and the fastest usable one, but has blind spots.**
   - It scores 91–94% on real asks, sub-second on the MacBook and on ai0's GPU.
   - It still sends 7–9 follow-ups to the inbox.
   - It scores 0% on "thanks", 0–13% on new subjects and 33% on two waiting.
   - Kev-0.8B is fast (84 ms on MLX) but 63–64%.
   - The two llama.cpp builds (CUDA on ai0, CPU on tts) give identical answers on all 105 cases.
     MLX bf16 differs from the quantized GGUFs on 9 of 105 for Kev-4B and 2 of 105 for Kev-0.8B.
8. **GLiNER2.5-Decide and Laya-multilingual can't do this task zero-shot.**
   - GLiNER picks by position. Reversing the option order flipped its synthetic picks from the
     first-listed `pr-812` (70 of 105) to the newly first `main` (72 of 105).
   - GLiNER also ran out of GPU memory on 8 of the longest real inputs.
   - Laya picks `pr-812` in either order (63 of 105), matching its model card's "near chance on
     typed decisions zero-shot".
9. **CPU inference on the iMac is too slow for routing.** Kev-0.8B p50 is 5.5 s and Kev-4B 15 s.

## Conclusions

1. Ship #5708's context. It fixes the bug for every LLM on its own.
2. Classifier model: **GLM-5.3-Flash through Zhipu's native API at low reasoning effort.**
   - 90%, with every follow-up kind at 100%.
   - p95 2.3 s, inside the 4 s timeout.
   - $0.13 per 1,000 routes.
3. Runner-up: **DeepSeek Flash.**
   - 86%, the steadiest latency (p95 1.5 s), $0.18 per 1,000.
   - Its Anthropic endpoint honors `thinking: disabled`, so it works through a direct
     Anthropic-format call.
4. Whatever the model, the classifier must:
   - keep the user's memory out of the call (finding 2);
   - turn reasoning off explicitly per provider (findings 3–5);
   - for GLM, call the native API.

   #5718 / #5720 implement the first two for direct Anthropic-format calls.
5. Not yet a decision model. Kev-4B's speed and real-ask accuracy make a Kev fine-tuned on the
   routing log the next experiment (`kev.train`). The harness's `/v1/systemone` client already
   speaks the request format of Kev, llama.cpp, hosted Jev and Cloudflare Clef.

## Caveats

- **Sample size.** 6–12 cases per kind and one pass per run; differences under about 5 points are
  noise. Lean vs deployed Haiku (90% → 80%) is the result most worth repeating.
- **Labels.** The real labels are one person's judgement. Real-case topic summaries are from the
  end of the period, a slight future leak.
- **Hosted Jev was not run** (no API key).
- **Prices** are official list prices at the time of the run:

  | model | input | cached | output | source |
  |---|---|---|---|---|
  | Haiku 4.5 | $1.00 | $0.10 | $5.00 | Anthropic |
  | GLM-5-Turbo | ¥5 | ¥1.2 | ¥22 | bigmodel.cn, under 32K input |
  | GLM-5.3-Flash | ¥0.8 | ¥0.23 | ¥2.8 | bigmodel.cn, standard |
  | DeepSeek `deepseek-flash` | $0.15 | $0.003 | $0.60 | DeepSeek, off-peak |
  | luna-6 (`gpt-5.6-luna`) | $0.20 | $0.02 | $1.20 | OpenAI |

  Prices are per million tokens; CNY is converted at ¥6.714 per USD. Notes:
  - GLM-5.3-Flash is half price for a limited time; not applied.
  - DeepSeek's off-peak rate matched the ¥0.20 actually billed for its two runs; peak is double.
  - luna-6 actually ran on a ChatGPT plan at no per-token cost.
- **DeepSeek naming.** DeepSeek's API offers only `deepseek-flash` and `deepseek-v4-pro` and
  rejects `deepseek-v4.1-flash`. "DeepSeek Flash" is its current Flash, which isn't
  version-confirmed as V4.1.
- **Lost run.** The first GLM-5-Turbo lean message-only run was overwritten by its thinking-on
  rerun (`tts-llm-glm-lean-thinkingon-rerun-message-only.jsonl`). The numbers quoted for it in the
  #5710 comment (75%, 6 / 74) have no surviving log.
