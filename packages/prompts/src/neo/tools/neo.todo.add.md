---
id: neo.todo.add
---
Add a todo to an open ask you own. For a human request, pass input. When a plain human message (not a reply) continues an open ask you own, also pass that askId: the daemon records the message on that ask, and later calls with that input alone reach it. Without askId it opens a new ask. For multi-PR work, use one PR per todo with its pack merge check. after is required on every todo and there is no default order: after [] waits for nothing, after [ids] waits for exactly those todos, and a call without after is refused. In a chain each todo after the first names the previous todo id; the queue starts it when that todo finishes. Once its PR opens, name that PR with neo.todo.edit addUrls on its own todo. A coding PR already tracked by another live todo on that ask is recorded without blocking; prefer continuing the original todo. neo.todo.edit addUrls only pins URLs to an existing PR-merge check. Pass title and a required check {pack, kind, params}; doneWhen is generated, never supplied. Use a completion check the installed pack supports; core.human_confirmed {questionId}, core.evidence {} (preferred: the daemon assigns the path and gives it to the worker; {path: absolute file path} only for a result the human should see), or core.deployed {repo: lsm/HyperNeo, sha: full commit}. A pack may reject malformed checks or record bookkeeping conditions. Workers are long-lived sessions: name them for the project and a number, never a task title. For local starts, the daemon names a new worker '<engine> <project> <n>'; pass target.name only to choose another project-style name. instruction is the task for a session and target says where it runs ({verb: start, adapter, place?} or {verb: send, ref}). Spell out the task: every step that needs work done gets its instruction and target when you add it; leave both out only for a step that just waits on its check, such as a merge or a deploy, since nothing runs a step without them. non-coding todos share one visible user folder across projects when place is omitted: ~/HyperNeo by default, or exactly the instance workspace path. A different place needs an exact path the user named in chat, even inside the workspace; never invent folders under home. Coding keeps its repository place. Coding send targets must be in the todo repository; mismatched or unknown worker remotes are refused. To give a running worker this task use target {verb: send, ref}; to attach work that is already doing it, add the todo without instruction or target and call neo.todo.bind {todoId, ref}, with after [] when it runs in parallel, since bind waits for unfinished prerequisites; without them the daemon checks the todo itself. named records what the human named for it (engine, session, repository, folder). A session the human named is sent to only through the ref work.find {session} returns as an exact match. A todo with an instruction and target starts by itself once what it waits for is finished and a worker slot is free; there is no start flag and no Start card. When the human must decide before the work runs, ask with neo.question.ask before you add it. priority (urgent, high, normal, low; default normal) orders waiting work, urgent first: set it from how urgent the human made it; it can change later with neo.todo.edit. Never start todos yourself.
