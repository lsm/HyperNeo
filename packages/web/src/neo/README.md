# Neo MVP

An opt-in entry inside the existing web package at `/neo`, included in the web build. The old `/neo/index.html` URL and `/neo/` redirect to `/neo`, preserving query parameters. Development, build preview, and production servers serve the same entry. The normal HyperNeo entry remains unchanged. Requires this branch's daemon (schema migration 279) and a configured model provider.

## Working loop

- Messages use existing sessions, message delivery and live subscriptions. One-off messages do not mechanically create concerns; Neo decides when continuity justifies one.
- `neo.message.send` provides the live composer's dedicated human intake boundary: a client request UUID identifies one ask, identical retries reuse its persisted prompt/delivery, and conflicting retries reject. Acceptance atomically stores the human input and existing delivery job without loading a coordinator or waiting for a query. No holder or worker is created by intake. Independent routing and request-scoped progress remain pending.
- The composer uses the reusable `useNeo.send` client for root and holder conversations, sends text/image content blocks, and clears only the submitted draft/files after a matching durable receipt. Rejected or unconfirmed requests retain them for an explicit same-identity retry; late replies cannot clear a reopened view's new text or show a stale error. Processing does not disable intake after acceptance. Identity and in-flight state are browser-memory-only; a refresh does not retain retry identity. There is no offline auto-send, model-response wait or retry loop.
- A 分身 is a durable concern record, independent of its coordinator conversation and execution sessions. Neo reads short summaries and consults the relevant holder for detailed context. Root Neo can create concerns, but existing context can only be revised by its holder or the human; corrections use revision protection.
- Neo can now consult a concern coordinator through `neo.concern.consult`. The existing holder session receives a bounded question through the durable mailbox, saves relevant context, and returns up to 4,000 characters through `neo.concern.respond`. Only root Neo may initiate consultations, and only the assigned holder may answer. Execution still needs a separate user-approved work card.
- Consultation receipts survive restarts, retry keys prevent duplicate requests, and only one consultation per concern may be pending. A terminal holder turn without an explicit answer returns a failure rather than borrowing an unrelated transcript response. Neo shows a small “Checking with…” status while pending; internal mailbox envelopes remain under conversation details, not human message bubbles.
- Root consultations record the runtime-bound `originMessageId`, recheck that input after holder opening, reject cross-input retry-key reuse, and carry the identity through existing return envelopes and snapshots. Legacy receipts and internal work-review consultations have a null origin rather than guessed attribution. Request-scoped presentation still needs its own slice.
- Work proposals record the admitted root/holder query's actual input ID, recheck liveness immediately before reservation, and reject another input reusing its request key without overwriting the original receipt. Snapshots and raw/holder-review evidence carry the recorded session/input pair. Legacy or manual RPC proposals have a null input origin. A holder's system input is not automatically a root human ask; human lineage follows stored input/receipt evidence, and request-scoped presentation remains a separate slice.
- The reusable read-only `NeoService.resolveAskOrigin` traces explicit stored human/system coordinator inputs through recorded consultation and terminal work receipts, including producer-owned holder reviews. Unknown, legacy, mixed, mismatched, cyclic or over-eight-hop lineage stays null. It is descriptive provenance, never authorization; routing and request-scoped presentation do not consume it yet.
- New root/holder SDK assistant and result messages retain their actual query input as `neoInputOrigin` in the existing persisted message JSON. This is a raw session/input pair, not an authorization grant or guessed root-human lineage. Unbound origins are null; ordinary sessions/workers and token streams are unchanged. Existing history is not backfilled, and correlated presentation remains a separate slice.
- Those coordinator responses also record `neoAskOrigin` using the existing bounded stored-lineage resolver. A delayed consultation or terminal work return retains its original human ask even after an unrelated ask is answered; unknown lineage is explicitly null and both provenance fields override provider-supplied values. This metadata survives ordinary message persistence/reload without authorizing any action. It does not yet group bubbles or drive per-ask progress/routing; legacy history and other runtimes are not backfilled.
- The live transcript consumes explicit `neoAskOrigin` for a compact reference on delayed replies following a different human ask. Clicking scrolls to that exact visible ask within this conversation; direct replies remain uncluttered and chronological order is unchanged. Null/legacy, cross-view, missing, duplicated, internal or truncated inputs never borrow the latest ask. This is provenance presentation, not independently routed progress or board attribution.
- Consultations have a provisional ten-minute wall-clock deadline from creation, including queue wait. A durable recovery job checks once a minute and startup recovery checks immediately; reply and context-write admission also enforce the deadline. “Stop waiting” closes that receipt and rejects its later writes/answers, without undoing context, deleting queued messages or stopping execution workers. It does not immediately interrupt the holder query; that query may finish, but is bounded by the original deadline. Retrying requires a new request key. Adaptive deadlines and automatic follow-up supersession remain future work.
- Root Neo has no native question tool: it asks a short question in conversational text and ends its input turn, so human clarification does not hold the query open. New root sessions and later queries on existing roots use the same policy. Direct-holder and ordinary worker question cards are unchanged; already-running legacy question waits are not forcibly canceled. The operations catalog remains available under each owning subsystem's admission rules, without a central Neo allowlist; coordinators still have no shell/file tools, native subagents or arbitrary external MCP servers.
- Work proposals show the actual brief and an optional immutable `targetSessionId` for an existing ordinary project/non-project execution chat. User-approved Start reuses that chat without changing its workspace, configuration, role or permissions; its bounded input asks it to return exact-work evidence through `neo.work.report`. Duplicate Start/recovery reuse the work UUID and existing mailbox/prompt deduplication. The card calls shared cancellation “Stop waiting”: it closes only this receipt, without interrupting other work. Null targets preserve a new, self-contained scratch worker in `$TMPDIR/hyperneo-neo-work/…` with dedicated interruption. There is no new execution engine.
- Concern-bound terminal responses go to the responsible holder through a durable consultation before root Neo receives its interpretation. The holder is asked to preserve relevant context, distinguish reported claims from verified facts, and return the useful conclusion without starting more work. Busy holders defer reviews until the current consultation settles; restart recovery resumes saved reports. One-off work still returns directly. Previously delivered or queued direct reports are not replayed through a holder. “Response ready” describes the raw execution response, not independently verified completion or a finished holder review; execution history stays inspectable even if the review fails.
- A completed reply's “Read result” detail uses its explicit current-view `neoInputOrigin` to match the exact raw or holder-reviewed work receipt, so interleaved tool results or unrelated asks do not erase or borrow its report. Explicit unknown/mismatched origins suppress chronological guesses; provenance-absent legacy history keeps its old projection without backfill. Partial replies never gain a completed-work detail and reports remain unverified claims.
- Concerns, conversations, proposals and results survive refresh/restart. Drafts are isolated while switching views but remain browser-memory-only. Reconnection refreshes snapshots and transcripts.
- Accent colors identify contexts without defining fixed categories. The concern card puts holders with proposed work, running work, or a pending context check ahead of quiet holders, then uses recent context activity. A proposed-work cue also appears on the parked mobile icon; one-off work does not create concern attention. Motion is subtle and respects reduced-motion settings.
- Neo keeps a global snapshot for the overview and concern navigation. Opening a 分身 also reads that holder's scoped snapshot for its work cards and pending checks; later changes refresh both, and a late result from a previously selected holder cannot replace the current view.
- Snapshots add optional `askOrigins` metadata for only their returned work/consultation receipts, keyed by exact kind/id. The daemon reuses its stored-input lineage resolver; a null origin means unknown, not the latest ask. Pending direct handoffs can resolve before execution, while null-origin internal reviews need their actual producer-owned request provenance. Older snapshots remain readable; per-request board presentation is separate from this data interface.
- `useNeo.projectBoard` exposes a pure concern-board projection of actual receipts and session references. Optional bounded daemon inventory adds recorded direct participants and outgoing resource links, without reverse-expanding shared containers into unrelated work. Missing metadata stays unknown; capture time and truncated kinds stay explicit; no resource or activity is invented.
- The optional “How Neo is handling things” overview or “How this is being handled” concern board renders this projection, not another transcript or a per-ask attribution claim. Opening reads up to 50 non-archived entries per kind through `daemon.snapshot`; Neo changes, reconnection, or explicit Refresh update an open board without polling. Closing, changing scope and unmounting invalidate late reads. Inline details show real briefs, returned claims, references and recorded outgoing links. Metadata is point-in-time and explicitly incomplete when truncated; session lifecycle never substitutes for live progress. The board uses existing theme tokens and creates no work.
- A full-width scroll surface runs behind the width-capped floating composer. Readable message bubbles stay in a narrower rail with a 160px minimum width. Names and local timestamps sit above each bubble (time today, date and time on other days); full timestamps are available on hover. Copy controls below each message copy its text, without metadata or internal tool output. The concerns card stays visible on wide screens and parks behind a header icon on smaller screens.
- One searchable, provider-grouped model picker and inline thinking buttons use existing session APIs. Duplicate provider/model entries are collapsed. Arrow keys move through results; Escape closes the picker and returns focus. Changes wait while Neo is working. No extra execution or provider settings are introduced.
- The model list shows names only in a taller list. The composer reuses HyperNeo's light-bulb thinking indicator. While Neo is queued or processing, three quiet breathing dots accompany a plain status line, without a bubble or repeated name. The line accepts variable-length activity text; the current source is the session processing state, including rate-limit cooldown. Request-scoped activity and independently attributed concurrent asks are not implemented yet. A completed reply can expose a short, turn-specific “What happened” trail beside Copy, with the technical session available from that trail. The second full SDK transcript is not embedded in the chat.
- Both sides render Markdown in a Charcoal & Apricot palette: warm headings for Neo, cool blue headings and bubbles for the human, amber emphasis, sage inline code, cyan links, and lavender quotes. Rich, non-persistent examples at `/neo?examples` include a local light/dark toggle that does not change app settings.
- The plus button, clipboard paste and whole-window drop area accept photos (PNG/JPEG/GIF/WebP, up to 3.75 MB each) and UTF-8 text files (up to 128 KB each). Up to six attachments and 8 MB combined payload are allowed. PDF, Office and other binary documents are explicitly unsupported. Text files are sent as fenced source content through the existing message path; photos use the existing image payload. Attachments alone can be sent. Pending attachments stay scoped to the conversation in browser memory, survive view switches, and are retained on failure; refresh clears them.
- Voice appears only when enabled with a configured endpoint/model. It reuses the recorder and transcription pipeline, inserts into the original conversation's draft for review, and exposes saved recordings for retry. Switching contexts cancels active capture; a transcription already underway returns to its original draft. Drafts remain memory-only, including transcribed text.

## Message themes

`neo.css` is the single customization point for Neo's palette. Its `.neo-shell` block sets the shared surface/text/border/accent tokens locally, without changing the rest of HyperNeo. Defaults use `light-dark()` and follow the existing app color scheme, including the system setting.

The semantic Markdown tokens are `--neo-markdown-strong`, `--neo-markdown-inline-code`, `--neo-markdown-link`, and `--neo-markdown-quote`. Both roles use these by default; quote backgrounds derive from the quote color. The `--neo-user-*` and `--neo-assistant-*` tokens allow independent overrides for accent, background, border, text, heading, emphasis, link, quote, quote background, code, code background, and table background. Name and timestamp colors use `--neo-message-label` and `--neo-message-time`. Role classes apply the tokens; components contain no bubble color utilities.

To create another palette, override variables on `.neo-shell` in a stylesheet loaded after `neo.css`, or in a shell's inline style. For example, changing one semantic token updates links on both sides without editing either component:

```css
.neo-shell {
  --neo-markdown-link: light-dark(#276879, #89c6d5);
}
```

Override `--neo-user-link` or `--neo-assistant-link` instead to change only one role. Shared Markdown structure and syntax-highlighting tokens (`--hljs-*`) continue to come from `styles.css`; they are not duplicated or changed globally. Live conversations and examples use the same component and stylesheet.

## Deliberate MVP limits

Neo can discover and inspect ordinary project/non-project chats with `daemon.session.inspect`: bounded metadata and recent excerpts, with an optional earlier-history cursor and explicit archived-history opt-in. It starts no SDK work and exposes no config/system prompt. Protected Space/execution and Neo-bound contexts retain their existing readers/holder consultation; this is on-demand inspection, not completed existing-world delegation or milestone acceptance.

Proposal and Start reuse the work-target resolver for exact existing execution-chat references. Missing, inactive, coordinator/holder or Space/task/workflow-owned contexts reject instead of guessing another executor or bypassing owner admission. Direct chat reuse is one thin adapter, not a fixed menu of execution modes; richer Space/manager delegation still uses its own operations and needs its own integrated acceptance.

Existing-chat work now has proposal, user-approved delivery, executor reporting instructions and the recipient-owned report operation wired. Queued shared-target receipts never infer completion from later SDK output; cancelled receipts reject late reports. Settled reports retain existing attributed, deduplicated returns; null/default targets retain dedicated-worker behavior. Runtime/operations regressions are not a substitute for real-provider existing-world dogfood acceptance.

Root Neo and holder SDK queries consume one input each, reusing their persistent session/history. Their operations server carries that input’s immutable runtime identity and live query-attempt check; prompt text and tool arguments cannot replace it. Other inputs remain in the existing queue. An already settled or expired consultation input is acknowledged without reaching the SDK, letting the next queued input advance. The finite stream does not wait for a response operation or successor, and a consultation deadline aborts only its own live query. Cleanup disposes its timer; an obsolete timer cannot abort a replacement. There is no additional coordinator mutex. Each new query may add startup latency. Root queries remain sequential; independent routing and per-ask progress are separate milestone work.

An input already admitted to the existing queue during a finite coordinator query now advances through completion-driven lifecycle handoff when that query settles; it need not wait for the delivery timeout or a manual start. Actual root and holder bindings are covered with delivery acknowledgements, one input per SDK query, exact UUID consumption and single-query ownership. Lifecycle guards still refuse unavailable successors. This does not shorten an ongoing SDK query or prove independently attributed routing, nonblocking human clarification or either complete milestone.

Consultation saves now use migration 280’s grant: the assigned holder, live request/deadline and captured context revision must match, even if the holder rereads newer context. Successful writes advance only their own grant. A conflict requires a fresh consultation, not another save retry. Direct human-to-holder SDK inputs retain ordinary revision checks, based on stored human-input provenance. Legacy ungranted consultations and holder calls without trusted input identity fail closed; alternate runtimes such as ACP do not yet supply this identity. Local human saves and root concern creation are unchanged. This does not prevent semantic mistakes within a valid request or automatically supersede ongoing work when a new chat message arrives.

Single-user local use. Execution can reuse an exact existing ordinary chat or create a self-contained scratch session; consultations reuse the concern coordinator. No automatic import/linking of existing Spaces or task histories, concern merge/archive, scheduling or proactive reminders. Consultation routing and interpretation are model-directed and may still be wrong; inspect the saved context and correct it conversationally. This UI shows the 50 newest work receipts plus up to 50 older proposed or running receipts; consultations are limited to 20. Full history remains in HyperNeo, but older active cards beyond this display cap are not shown. Holder review uses the same consultation lifecycle and does not automatically retry a settled failed review. This is bounded Neo↔holder coordination, not continuous autonomous concern management.

The old `NeoPreview` component remains a test fixture, not the live entry. No sample concerns are seeded in the live app.

Neo's session has no selected workspace. Its SDK process uses an internal, per-session runtime directory instead of inheriting the daemon's launch folder or worktree. The coordinator prompt treats that directory as plumbing, answers at conversational length by default, and asks what a vague request such as “brief” refers to when the snapshot has no clear subject. Delegated execution sessions retain their own separate workspace rules.

## Local run

Use an isolated `DB_PATH` and workspace root for testing. Run the daemon, then start web with `DAEMON_URL` pointing to its port. Existing provider discovery is reused; never copy credentials into this package.

Browser acceptance checks: one-off question; continuing concern; correction reuses it; reload retains both; approve a bounded draft-only task; inspect returned result; open the concern; answer a choice card; switch back with the original draft intact; inspect desktop and mobile layout. Test cancellation, duplicate actions, scope restrictions and terminal attribution in the focused unit suite.

## Coordinator input handoff

After a coordinator query settles, an already-admitted successor is driven through the existing query lifecycle without waiting for its delivery timeout or creating another queue. A synchronous admission pipeline rechecks persisted coordinator binding, query generation, interrupt epoch, session availability and queue ownership under the existing delivery lock, including after asynchronous startup preparation. Manual mode, SDK-resume waiting, limit recovery, cleanup, interruption and stale generations do not start successors; ordinary sessions and workers retain their existing streaming behavior. The regressions exercise both root and holder bindings through real AgentSession, SQLite delivery state and query lifecycle with mocked SDK subprocesses, including context-clear and asynchronous ownership boundaries. Root input isolation (#5232) and handoff (#5237) are integrated; this is runtime characterization, not real-provider or complete per-ask routing acceptance. SDK startup can still add latency and root queries remain sequential.

## Recipient-owned reports

The `neo.work.report` operation calls the reusable recipient-report pipeline through the existing operations interface. Execution sessions can discover it without a Neo role, but only the actual MCP session recorded on the exact work receipt may report; root/holder bindings, local-human RPC, internal callers and claimed argument identities cannot impersonate it. Explicit `reported`/`failed` evidence is capped at 12,000 characters and returned as a minimal receipt. The existing repository CAS and return path preserve origin-session/message provenance, reject cancelled or conflicting reports, and permit exact retries without rewriting the settled row or duplicating its return. Concern-bound evidence still goes through its holder review. A report is a claim, not verified completion; no arbitrary later SDK output is consumed. Real-provider delegated work with unrelated intake and request-scoped presentation still needs integrated verification.
